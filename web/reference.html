Language reference · F0

Science

A compiled language for scientific computing and machine learning. Native binaries through LLVM, memory managed by ownership and borrows verified at compile time with no garbage collector and no lifetime annotations. Blocks are indentation; keywords are English words where no symbol is universal, and symbols where one is.

This page is written for somebody who knows Python and NumPy and has never written Rust. Each section says what a construct is, why the language has it, how it behaves at the edges, and what it costs — because a syntax sample shows you the first of those and none of the other three.

Getting started#

A file is a module, and a file's top-level statements are its program. There is no project file, no manifest and no scaffolding — not even a main. Save this as hello.science. 

type Reading:
    channel: Int
    counts: Int

def total(first: Reading, second: Reading) -> Int:
    first.counts + second.counts

let a be Reading(channel: 1, counts: 4_900)
let b be Reading(channel: 2, counts: 1_180)

print(f"channels {a.channel} and {b.channel} hold {total(a, b)} counts")
# channels 1 and 2 hold 6080 counts
$ sciencec check hello.science
$ echo $?
0
$ sciencec build hello.science
$ ./hello
channels 1 and 2 hold 6080 counts

Six things in eleven lines are worth naming before anything else, because each is a place a Python reader's expectations will quietly disagree with the language.

The statements at the top level are the program. There is no def main here and there must not be one: a file whose top level holds statements is a script, the compiler writes the main that runs them, and writing a second one yourself is SC0117. Scripts and programs is the section; the rule exists so that a two-line analysis script and a library module are the same file kind with no ceremony between them.

Blocks are indentation, and only spaces. A tab in the indentation is SC0003 with no attempt to guess a width. That is stricter than Python, which resolves the mixture by a rule most people could not state, and it is strict for a stated reason: a tab's width depends on how the file is displayed, so a file indented with both would mean different things to two readers of the same bytes.

let … be, not =. The word is there because = has two unrelated meanings in the languages this audience writes — binding in a program, equality in a paper — and a language that keeps the symbol for binding has to spell equality == to get out of the way. Science keeps the mathematical reading: is compares, be binds, and neither has a second spelling.

Reading(channel: …, counts: …) constructs with named arguments, in any order. Ordinary function calls are positional; record construction is not, and the asymmetry is deliberate. A record's fields have names the author chose, and a constructor call that lists four integers in an order you have to look up is one of the commonest places a program is silently wrong.

f"…" interpolates and "…" does not. A brace in a plain string literal is a brace, which is what makes JSON and LaTeX writable without escaping; the f prefix is what turns {total(a, b)} into a value. Any expression may stand in a hole. Strings and formatting has the rest.

check is silent on a clean file and exits 0. It drops into a shell script or a CI job without ceremony. Anything it finds goes to stderr with a code, a primary span and, where a mechanical fix exists, the exact replacement text, so an editor or an agent can apply it without reading the prose. Dumps go to stdout. Warnings alone do not fail the run.

What works today#

Documentation for an unfinished language is more useful when it says exactly where the edge is. This is where it is, area by area, as of this build — both halves, because a reference that overstates is one a single experiment destroys.

The front end: what check runs

sciencec check is seven phases, in this order, with a gate after each of the first three that stops the run when something was reported as an error: lex → parse → resolve → type-check (aliases, declarations, then bidirectional checking into THIR) → MIR lowering → the call graph → region inference. The gates are why a file with a syntax error never reports a borrow error: the later phase would be reasoning about a recovery rather than about the program.

The back end: what build emits, and what it refuses

The discipline is that nothing is lowered until an execution test has run it. Everything else is refused with SC0400 and a sentence naming the construct. That is a deliberately unusual choice — most compilers lower optimistically and find out later — and the reason is in this back end's own record: of the thirteen things reading the specification could not have established, three were silent miscompiles that verified, linked and ran. A main that never wrote its return value. A null test that loaded a fat pointer. A store eight bytes wide into a one-byte slot. None of those is a crash; every one of them is a number.

Scripts and programs#

A file's top-level statements, in source order, are the body of an implicit def main() -> Error?. That is the whole of script mode: there is no second file kind, no flag, and no module-initialisation phase. 

def clip(value: Int, limit: Int) -> Int:
    if value > limit:
        limit
    else:
        value

# Statements and declarations interleave, and a statement may call a
# function declared below it.
let raw be 1_200
print(f"clipped to {clip(raw, 1_000)}")
# clipped to 1000

let low be clip(-5, 1_000)
print(f"and {low} passes through")
# and -5 passes through

Why the language has this at all. The people Science is for write a great many files that are ten lines long and run once, and a language that demands a main before it will print anything has put a ceremony between the user and the first correct result. The cost of admitting statements at the top level is a grammar decision that cannot be retrofitted — whether a file's top level is a sequence of declarations or a sequence of items and statements changes the parser, the resolver and every diagnostic that says "a module holds declarations only" — which is why it is settled in F0 although nothing else about the interactive tier is.

What a top level may hold, and how it was built

The production is one line long and it gained one alternative: top_level := item | stmt. An item is any of use, type, choice, interface, def, const, a Type has: block and a Type implements I line. A statement is the same Stmt the parser already produced for function bodies. No new statement kind, no new expression form, no new keyword and no new reserved word was added to buy this.

It ships as a desugaring, and that is worth knowing because it leaks in exactly one place. parse_module gathers the top-level statements and appends one generated def main() -> Error? whose body they are. No phase after the parser learns the word "script": the resolver, the type checker, MIR, region inference and codegen all see an ordinary function. The leak is that a generated node has no source text, so sciencec tools --json --all-functions on a script lists a main nobody wrote. It is pinned by a test rather than filtered, because filtering it out means teaching the driver about scripts, which is the one thing the desugaring buys out.

One line of the grammar needs two tokens to disambiguate. Both an implementation header and a statement may begin with an identifier. The rule is exact rather than heuristic: a top-level logical line beginning with an identifier is an implementation header if and only if the reserved word implements or has occurs in it at bracket depth zero before its : or its end. Neither word can occur in an expression, a path, a type or an assignment target, so this is one linear scan of one line with no backtracking and no speculative parse. 

type Reading:
    channel: Int

Reading has:                          # an item: `has` at depth zero
    def first() -> Reading:
        Reading(channel: 1)

let r be Reading.first()              # a statement
let mutable n be r.channel
n be n + 40                           # a statement: assignment, no `has`

print(f"{r.channel} {n}")
# 1 41

The empty file is a program. A file with nothing in it, and a file holding only comments, both check clean and mean "do nothing, exit 0". There is no empty program diagnostic. The implementation consequence is smaller than it sounds and is stated here because it caught the back end: an empty script body produces no MIR body at all, so "falling off the end" is not a path any execution test can drive from Science source.

Statements run only in the entry file

Importing a module never runs anything: there is no module-initialisation phase, and a top-level statement in a file that something else uses is SC0213. The same file is a perfectly good script when it is the file you named, and a broken module the moment another file imports it, and the diagnostic shows both halves — the statement that would never run, and the use line that made it a module.

How the compiler tells a script body from a written main, given that no phase below the parser knows about scripts. It tests the one property the desugaring leaves behind: the generated main's name span is zero width, where a written one covers four bytes. A test pins that against a real parse, so if the parser ever gives the generated name a span, the test breaks rather than SC0213 quietly ceasing to fire.

Why the rule is strict rather than a warning. The alternatives were: run them once at first import, which is what Python, Ruby and Julia do and which makes use an effect — a line that can read a file, allocate or panic, invisibly, at its use site; do not run them and say nothing, which is the one thing a project whose UI tests compare diagnostics byte for byte should not choose; or warn, which data-io.md already dismissed by observing that SettingWithCopyWarning is a warning nobody reads. Either it matters or it does not. Relaxing this later — allow, do not run, warn — is source-compatible; tightening it later would not be.

A directory module needs no special case. mod.science is never an entry by rule two, which names main.science specifically, and it is reached by use whenever its directory is, so top-level statements in a mod.science are always SC0213.

Ordering, and the one direction that does not cross

There is no hoisting and no reordering. The statements run in source order. What is not ordered is declaration: a statement may call a function declared below it, because the resolver collects every definition in every module before it looks at a single body. By the time anything is resolved, everything is known, with no fixed point. The practical consequence for this audience is that a script's helper functions can go at the bottom, which is not true of MATLAB and not true of C.

The one thing that does not cross the line is the other way round: a named item does not close over the top level, so a def cannot see a top-level let. That asymmetry is enforced by construction — items are resolved in a scope the script bindings are not in — so the diagnostic reserved for it, SC0212, has never had anything to report and is not implemented. What you get is the ordinary not-found error: 

error[SC0200]: cannot find `threshold` in this scope
 --> analysis.science:4:13
  |
4 |     value > threshold
  |             ^^^^^^^^^ not found

Three reasons the ban is there, and only the third is unobvious. It would make item bodies depend on execution order, so a function called before line 1 has run would read an uninitialised binding — C++'s static initialisation order fiasco, and Python's call-time NameError. It would put a hole in local inference, because one function's body would depend on another function's inferred local across a boundary drawn to keep that closed. And it inverts the region engine's analysis order into a genuine cycle: functions are analysed in reverse topological order of the call graph, callees before callers, so keep is analysed before the script body — but the binding's region is a fact about the script body's MIR. That is a dependency cycle across the call graph, which the strongly-connected-component fixed point does not cover, because it is not a call cycle.

A closure sees the top level; a named item does not. The closure is inside the script body, so its capture is an ordinary capture of an ordinary local and needs no rule of its own. That line is also what makes the F1 notebook tier tractable: because no item body can read a script binding, invalidating a cell invalidates statements downstream of it and never a function body — the dependency edges from cells go forward into cells and never sideways into items.

A top-level let binds a local of the script body, not a global and not a static. Its scope is the rest of the top level. It drops at the end of the script, in reverse declaration order, before the process exits — and a panic does not run drops, because panic is abort, so a panicking script leaves its temporary directory behind. Choosing a static instead would have bought exactly one thing, item bodies reading it, which the paragraph above already forbids for independent reasons; and it would have cost a 'static region, an at-exit registry with an order, and an initialisation-order analysis. All of the cost, none of the benefit.

public is an item modifier and a statement declares no name to export, so it is refused where a reader will first try it: 

error[SC0107]: `public` has no meaning on a statement
 --> analysis.science:1:1
  |
1 | public let n be 1
  | ^^^^^^ a statement declares no name to export
  |
  = help: the statement runs either way: delete `public `

The exit-code contract

The script body's signature is def main() -> Error?, and that signature is the contract. There is no second mechanism, no sys.exit, and no status to return by hand. The signature is Error? rather than () because if err?: return err is the idiom for every fallible call, and a top level on which that idiom does not typecheck is a top level on which the language's own error model cannot be used. A script is mostly IO and IO is mostly fallible.

Third: the script body's tail is always a generated null, never its last statement. Promoting a trailing expression to the tail, which is what block parsing does everywhere else, would make the value of print("hello") the script's return value — and () is not an Error?. Two things are deliberately absent and both would be one-line additions that cost a permanent name. There is no exit(code): the free function list is closed, and an exit code other than 0 or 1 has no caller yet. There is no argv: the process environment belongs to a library, not to the grammar. A leading #! line is a # comment and already lexes correctly; making it executable is a filesystem question and not a language one.

That diagnostic carries no applicable fix, and the absence is deliberate rather than an omission: there are two reasonable repairs and a compiler cannot choose between them. Everywhere a mechanical fix exists this compiler prints the exact replacement text; where two exist it prints neither, because a tool that applies the wrong one of two is worse than a tool that applies none. When it fires, the script body is not generated at all, so one mistake stays one diagnostic instead of cascading into every statement.

The three alternatives were priced and all three lose. Statements run, then main runs is Python's if __name__ == "__main__": wart with the condition made implicit instead of explicit, which is strictly worse, because at least Python's is visible in the source. main wins and the statements are module initialisation reintroduces the initialisation phase that the module rule above exists to delete. The statements win and main is dead is silently dead code. A file with a main and no top-level statements is of course fine, and is what a library's entry file looks like.

What names the entry, and what a crate is

Rule one: the file named on the command line. Rule two was to be main.science at the crate root when no file is named, and it is not built — it needs a crate root with no file to derive one from, which is the package manager's question. There is no sciencec run either; the commands are check, build, fmt, tools, ast, resolve and tokens.

A crate is one entry file plus the transitive closure of the modules its use declarations name, rooted at the entry file's directory. That definition is the implementation's; the design note that both rules lean on never defines the term. So sciencec check a.science b.science is two crates, one per name, and not one crate of two files — because each file named is an entry, and folding the command line into a single crate would make every file after the first a non-entry and report SC0213 on all of them. That is the opposite of what script mode is for. 

$ sciencec check plots.science
error[SC0213]: top-level statements in a module that is not the entry point
1 error

$ sciencec check clean.science
$ echo "exit=$?"
exit=0

One consequence is worth stating because it has bitten a measurement: the same declaration in two files numbered in two orders used to produce two different const-expression normal forms, because the atom order was derived from a declaration id and ids are handed out in command-line order. That is fixed — the order comes from a canonical path now — and it is recorded in Types as the shape of the bug that a.science b.science can still cause elsewhere.

If you are arriving from Python: the file is the program, and that is where the resemblance stops

A .science file with statements in it runs those statements, top to bottom, exactly as a .py file does. Four things then differ, and three of them will catch you in the first hour.

Importing runs nothing. Python executes a module's body on first import and caches it; Science does not, and a statement in an imported file is a compile error. There is no if __name__ == "__main__":, because there is nothing to guard against. A function cannot read a script variable. Python resolves a global at call time, so a def above a threshold = 0.5 works as long as nobody calls it too early; here it does not resolve at all. The exit code is a return value. There is no sys.exit; the script body returns Error? and the runtime maps it to 0 or 1. And the last expression of the file is not the program's value — the script body's tail is a generated null, so a bare expression at the end of a file is a statement whose value is discarded, not a result.

Bindings and literals#

let … be introduces a name. be on its own assigns to one that already exists. A binding is immutable unless it is declared mutable. 

let title be "Regions"             # immutable, and the type is inferred
let mutable count be 0             # `mutable` is what makes assignment legal
let width: Int be 768              # the annotation is optional everywhere

count be 3                         # assignment: `be` without `let`
print(f"{title}: {count} runs at {width} columns")
# Regions: 3 runs at 768 columns

Every form of let, and the one that surprises people

mutable distributing over every name in a destructuring let is a decision, not an accident. The list receives one tuple, and a form in which half the names were mutable would need a second mutable in a position nothing else in the language puts one. So let mutable frame, err be read_csv(…) makes both frame and err assignable, which is almost always more than the caller wanted and is the cheaper of the two wrongs.

Shadowing is allowed, and the right-hand side sees the old binding. A second let with the same name in the same scope introduces a new binding rather than assigning to the old one, and the initialiser is evaluated before the new name is in scope, so let n be n + 10 reads the previous n. This is the Rust rule and not the Python one; in Python there is no second binding to make, only a rebinding. 

let n be 1
let n be 2                         # a second binding, not an assignment
print(f"{n}")
# 2

let n be n + 10                    # the `n` on the right is the one above
print(f"{n}")
# 12

Immutable is the default, and this is the first real cost of the language. In NumPy every name is rebindable and every array is mutable, and nothing asks which you meant. Here the compiler asks once, at the binding, and in exchange a reader of let title be … knows without searching the function that no line below changes it. The word is mutable and not mut because abbreviated keywords lose an argument the language still holds to: count the spelling across Fortran, MATLAB, R, Julia, Python, JavaScript and PHP before shortening a word — not across the corpus a model was trained on.

None of that is enforced today, and the gap is total. Assigning to a binding that was never declared mutable is accepted by every phase, builds, and runs. Writing through a shared borrow is accepted too. There is no diagnostic to quote here because none is emitted; the code below is a whole program that checks clean, builds, and prints 3. Assignment, and the two spellings that do not exist

Assignment is a statement, not an expression. It has no rung on the precedence ladder and produces no value, so if (x be 1): is not something the grammar can express. There is also no compound assignment: count be count + 1 and never count += 1. One spelling instead of two, and a rebinding inside a loop stays visible on the line where it happens.

Numbers

Numeric types are written out and never converted implicitly. I8 … I64, U8 … U64, F16, BF16, F32, F64, with Int aliasing I64 and Float aliasing F64. as is always written, including where it loses precision, because a language that silently widens an F32 to an F64 has made a decision about your memory budget that you did not ask for.

Four numeric behaviours are decided here rather than left open, because a numeric language cannot leave them open. Integer overflow panics in debug builds and wraps in release. Integer division truncates toward zero and % takes the sign of the dividend. as from float to integer saturates, and NaN becomes zero. And F32 and F64 implement Eq but not Ord, because NaN has no total order — so sorting floats takes an explicit total-order function rather than silently producing a permutation that depends on where the NaNs started. Reductions have a defined order unless they are marked unordered, and a result that differs between runs is opt-in, because this is a language whose users publish.

One of those four is emitted, and the others are not. Saturating float-to-integer casts work in both directions and on NaN. Integer / and % are refused by the back end entirely, and so are shifts. It costs four things and the design names them. Display, Inspect, and what a hole requires

A plain hole renders its value through Display, which is the spelling a person reads. {x!i} renders through Inspect, which is the spelling a program reads — print(f"{name}") gives A12 and print(f"{name!i}") gives "A12", quotes included. The division matters most for units, where Display prints the typeset m/s² and Inspect prints 9.80665<m/s^2>, which pastes back into a program unchanged.

Both take a Formatter, and that is what lets a user type honour a spec at all. The receiver is self, the shared borrow, and that is where the does-not-consume guarantee comes from. Neither Formatter nor FormatSpec is in the prelude, so the block below is the specification and not a listing — writing it in a file gives SC0200, cannot find Formatter in this scope. What a program can write today is an implements Display: block with whatever method shape it likes, because nothing checks a block against its interface. changing 

interface Display:
    def display(self, into: mutable borrowed Formatter)

interface Inspect:
    def inspect(self, into: mutable borrowed Formatter)

Formatter has:
    def text(mutable self, value: borrowed String)    # pads, per the spec
    def raw(mutable self, value: borrowed String)     # does not pad
    def number(mutable self, value: F64)
    def integer(mutable self, value: I64)
    def spec(self) -> FormatSpec

FormatSpec is a plain record of nullable fields — fill, align, sign, width, precision, code, alternate, grouping — for an implementation that needs to branch on it. DisplayNumber is a marker with no methods that grants a type the numeric codes; it says they are meaningful for the type and cannot prove the implementation honours them. The check is type-level and that is where it stops.

Why !i and not Rust's {x:?}. This is the one place Science must not copy Rust, and the reason is one character wide: ? is already the presence test, so f"{err?}" prints true — the error is present — and f"{err:?}" would print the error itself. One colon apart, one a Bool and the other the value. That is not a collision a language should ship. !i also leaves {x!i:>20} well-formed, which {x:?>20} never was in Rust either.

Three things deliberately do not implement Display, and meeting them is how a reader learns the rule. A T? does not, until it is narrowed — printing a possibly-null value must be a decision, because a silent null or an empty cell in a published table is the failure this prevents. Arrays and maps do not; they implement Inspect, because there is no one right way to show a million rows to a person and there is exactly one right way to show them to a debugger. Unicode, and where the line is drawn

Unicode letters are legal in identifiers. σ, Δt, μ and χ2 are names. The boundary is the Unicode category and not taste: χ2 and not χ², because a superscript two is a number rather than a letter, and neither are ∇, ∂ or ℏ, which are symbols. Identifiers are normalised to NFC when they are lexed — one call in the lexer, and without it é as one scalar and é as e plus a combining accent are two different identifiers rendering identically. A single identifier that mixes scripts is SC0015, a warning — on mixing within one name, because Α, А and A are three different characters that look the same, so σ alone and σ_max are both fine.

≤, ≥, ≠, ∑, √, × and their relatives are not operators and are not accepted as aliases for anything. <= is the only spelling of <=. The design concedes the strongest counter-argument rather than hiding it: ≤ to <= is mechanically canonicalisable by a formatter, so the "permanent drift" argument that killed the word forms of the comparisons does not transfer here, and pretending it does would be dishonest. What is left is three things: an input problem, since no standard keyboard produces ≤; homoglyphs, which are worse — U+2212 MINUS SIGN is not -, U+2215 DIVISION SLASH is not /, and every one of those arrives by paste from a PDF; and the observation that ∑ is not an operator at all but a binder with a bound variable, an index range and a body, so what you would actually get is ∑(xs), a function call wearing a costume, where xs.sum() already exists. The recommendation if it is ever revisited is editor-side rendering: the file contains <= and the editor displays ≤.

Doc comments are ##, and there is no docstring

A documentation comment is a run of ## lines immediately preceding a declaration — a module, a function, a type, a choice, an interface, a const, a type alias, a field, a variant, an interface member or an implements block. The first line, up to the first blank ##, is the summary; the content is Markdown; there are no @param tags, because the parameter names and types are in the signature and a tag that restates them is a second copy that goes stale. 

## Spectral preprocessing.
##
## Everything here assumes the dark current has been subtracted.

## A single detector reading.
type Row:
    ## Instrument identifier, as written in the run log.
    station: String
    ## Channel count. Always 768; this is checked on load.
    channels: Int

## What went wrong while reading a run.
choice LoadError:
    ## The file had a channel count other than 768.
    WrongChannelCount(Int)
    ## The file was unreadable or absent.
    Unreadable(String)

Why not """…""". Most things that need documentation have no body — a field, a variant, a const, an alias, a module — so a docstring form covers functions and then needs a second form for everything else. It would require adding a triple-quoted literal, with its own indentation rule to argue about forever. And a docstring in the body is a value in Python and would be a lie here: an expression statement with no effect that the compiler silently treats as metadata. ## also composes correctly with # — a # TODO beside a doc comment stays an ordinary comment, a distinction a docstring form cannot make at all. There is one sigil and no module-level second one, because modules are files and position is unambiguous.

What they cost: nothing at run time. The lexer keeps ## runs as trivia attached to the following token, the parser attaches them to the node, and they survive into HIR — and that much must happen in F0, because once the lexer discards them every tool downstream is built assuming they are gone. sciencec emits them into a metadata section of the object file: a string table plus an index from fully-qualified name to offset, static data, not reachable from any code path, strippable.

A ## run attached to nothing — at the end of a file, or separated from the next declaration by a blank line — is specified as SC0176, a warning with the fix make it #. It is not implemented: a stray ## run checks clean and silently documents nothing, which is precisely the silent failure mode the diagnostic exists to prevent. changing

Doc tests are specified and are F1. A fenced science block inside a ## run is compiled and run; science,no_run is compiled only; science,fails must fail and the tool checks the diagnostic code; and a neighbouring output fence is compared to stdout byte for byte, which makes a doc comment a test of the formatting too. The reason it matters more here than elsewhere: Science has no training corpus, so the material a model will learn this language from is its documentation — and doc tests are what make it impossible for that documentation to contain an example that does not compile. The same argument is why this page extracts and checks its own listings.

A choice you mean as an error type: two rules decide whether it is guarded, and only one of them is about the type

SC0140 — the diagnostic that makes an untested error binding a compile error, and the whole reason this language can use a returned E? where Go uses a returned error — was specified as marking every binding whose type is an E? where E implements Error. Read literally, that leaves the guard off exactly the program a beginner writes: a bare choice with no implements line, returned as the second half of a pair. It is not hypothetical — examples/00_kitchen_sink.science declares three choice types meant as errors and writes implements Error for one of them.

So the implementation carries a type test and a position test, and either one is enough. The type test is the specified one, discharged against written implementations: any Error, and any type the crate declares implements Error:. The position test is the second slot of a fallible pair — a binding that came from a -> (T, E?) return — and it fires whatever E is. Both programs below are reported.

Const generics, and the arithmetic they admit

type Grid of (T, const ROWS: Int, const COLS: Int):
    cells: Array of T

type Padded of (T, const N: Int):
    cells: Array of T
    grown: Padded of (T, N + 1)
    shrunk: Padded of (T, N - 1)
    tripled: Padded of (T, N * 3)
    doubled: Padded of (T, 2 * N)

Const generics are in the core because tensor shapes are built out of them. Tensor of (F32, (batch, 768)) carries 768 as a generic argument, and 768 is not a type. Retrofitting that later means reopening the parser, the resolver and every snapshot, so it is here in F0 even though tensors are not.

The grammar is five operators and no more: +, binary -, unary -, * and /, with * and / each requiring an integer literal on one side. That is the complete list, forever, and every addition to it is an addition to the normaliser, the equality procedure, the diagnostic renderer and the monomorphisation key. There is no %, no **, no max, no min, no comparison, no conditional, no function call, no const fn, no recursion and no escape hatch.

So the arithmetic is linear by grammar, not by a check run afterwards: N * M for two parameters is not a program the parser can build a node for, and it is reported there.

The normal form is a thing you can see

A const expression is normalised to k + Σ cᵢ·aᵢ: a constant, then coefficient-and-atom terms with the atoms in a total order stable across compilations. Equality is structural equality of that form, so A + B and B + A are the same type and a function may be declared with one and return the other. It is one linear merge over a sorted term list, with no fixed point and no possibility of non-termination, because no production in the grammar grows an expression. 

type Buf of (const N: Int):
    x: Int

def same of (const A: Int, const B: Int)(p: Buf of (A + B)) -> Buf of (B + A):
    p

And when two forms are genuinely different, the diagnostic prints the normal form rather than the source, which is the part worth seeing: A + A comes back as 2*A, so a reader who wrote k + 1 on one side and 1 + k on the other can tell at a glance that the ordering is not the problem. 

error[SC0525]: expected `Buf of 2*A`, found `Buf of A + B`
 --> buf.science:5:5
  |
5 |     p
  |     ^ this is `Buf of A + B`

Why refuse the general case at all? Because type equality on Grid of (T, ROWS, COLS) is const equality, and four separate things have to agree about it — type equality, shape equality, index bounds, and the key that decides whether two monomorphisations are the same function. Four implementations of "are these two extents the same?" is four answers, and the fourth one is a linker emitting two symbols for one function. A linear form normalises to a canonical k + Σ cᵢ·aᵢ; structural equality on that form is sound and complete, because the forms are the free ℤ-module on the parameters and evaluating at the basis vectors recovers the coefficients; and the normaliser never receives a non-linear input because the grammar admits none.

The cost is real and the design admits it. Rust's generic_const_exprs has been unstable since 2020, and it did not stall on normalising N + 1 against 1 + N — that part was understood early. It stalled on three things: its expression language is const fn, so equality of two const expressions is equality of two programs and no normal form can exist; it must prove a const expression well-formed before the parameter is known, which needs a predicate language and an entailment checker; and it may not report at instantiation, because separate compilation and dyn rest on the generic having been checked in the abstract. Science's answer to the first is the closed grammar above; to the second, refusal; and to the third, that it monomorphises everything anyway.

So Science pays for the refusal in post-monomorphisation errors: a library can ship a signature that breaks for your shape, and you meet the error inside code you did not write. The obligations are two rather than an open-ended set — a negative extent, and the solvability of const-argument inference — and the mitigation is that the diagnostic must name the instantiation, the parameter, the value and the call that produced it. If that chain is not rendered well, the decision is indefensible. The retreat is safe in one direction: const predicates in a where clause can be added later and every program that compiles today keeps compiling, because a predicate only rejects instantiations that would have failed anyway.

One amendment the implementation forced, and it is the kind worth recording: the normal form is the monomorphisation key, and the atom order is derived from a declaration's canonical path. The original claim — that the order is stable across runs without a hash — is false, and it is falsified by its own second clause: sciencec check a.science b.science and the same two files in the other order number their declarations differently. Within one compilation that changed no answer, because equality sorts both sides with the same function; what it changed was the serialised key, so the same program could produce different symbol names depending on how it was invoked — a cache miss rather than an error, which is the worst way to find out. The order comes from a canonical path and an index now, and the cost of the fix is that renaming a const parameter can reorder a normal form where renumbering a file no longer can.

T?, and the three things it is not

T? is a distinct type, not a union and not a subtype of T. T coerces into T? implicitly; T? never coerces to T. There is no Option, so there is nothing to construct — the present case is the value itself and the absent case is the literal null — and equally there is no map, no unwrap_or and no is_some, because there is no type left for those methods to hang off. The whole interface is the presence test ? and the narrowing it performs.

T?? is an error rather than a flattening. The parser builds two nullable nodes and the type checker collapses them, because a presence test on a presence test is never what anyone meant. The diagnostic is one of the better ones in the compiler and it explains the model in its note: 

error[SC0520]: a type is nullable once
 --> opt.science:1:14
  |
1 | def f(x: Int??) -> Int:
  |          ---- already nullable here
  |              ^ this `?` adds nothing the first one did not
  |
  = note: `T?` is a distinct type holding a `T` or `null`, not a union, so there is no second absence for a second `?` to describe
  = help: the type is `T?`: delete `?`

What it costs in memory. A pointer-like T uses the null niche, so (borrowed T)? is one word. A T with no niche gets a discriminant byte, which is why an Int? occupies two words. An (any I)? is a nullable fat pointer with the niche in the data pointer, so it is two words and not three; the vtable pointer of a null interface object is undefined and never read. The two-word Int? is also the direct cause of the interpolation failure recorded in Strings and formatting: narrowing is a fact about the checker's view of a place and the layout is not narrowed with it.

Narrowing itself belongs to Errors, where the idiom lives, but one rule belongs here because it is a property of the type: narrowing is a fact about a place — a local, or a field projection from a narrowed place — and it is invalidated by any write to that place or to a prefix of it. config.port? narrows config.port and not config; writing to config invalidates it and writing to config.other does not.

Closures have a type, and it has no keyword

def apply(f: (Int) -> Bool, x: Int) -> Bool:
    f(x)

# `->` is right-associative, and `?` binds tighter than `->`,
# so a nullable closure needs its own parentheses.
type Pipeline:
    step: ((Int) -> Bool)?
    stages: Array of ((Int) -> Bool)
    curried: (Int) -> (Int) -> Bool

def twice(f: (Int) -> Int, x: Int) -> Int where Int: Eq:
    f(f(x))

(A) -> B reads as takes an A, gives a B. It is what Kotlin and Swift write exactly, what TypeScript writes with =>, and what the ML family writes with the arrow alone. The earlier spelling was function(A) returns B, which read as a noun naming what the parameter is; once returns became -> and function became def, the mechanical carry-over def(A) -> B was left naming nothing — a declaration that lost its name. The bare arrow sidesteps the problem by having no word to be the wrong part of speech, and it puts no new word on the reserved list. fn(A) -> B lost the audience test one to seven, and the one is PHP.

It parses on one token of lookahead and no backtracking: parse_paren_type reads (), (T) or (A, B) to completion, and then one peek decides — -> means that was a parameter list, anything else means it was a tuple. That is why a fallible return type -> (Config, Error?) stays a tuple: what follows it is : or where, never an arrow.

Three edge cases, all of which you will meet. It is right-associative, so (A) -> (B) -> C is (A) -> ((B) -> C), which is currying and the only useful reading. ? binds tighter than ->, so (A) -> B? is a closure returning a nullable and a nullable closure is ((A) -> B)?. And as a generic argument it needs its own parentheses — Array of ((Int) -> Bool) — for exactly the reason Map of (String, Int) does.

That last one does not fail; it means something else. Array of (Int) -> Bool parses cleanly, because the peek after (Int) finds an arrow and builds a closure type out of everything to its left. The field's type is (Array of Int) -> Bool: a closure that takes an array of integers. No diagnostic, no warning, and a type error somewhere downstream that names a type nobody wrote. It is the one silent misreading in the type grammar, and the only defence is the parentheses. 

error[SC0525]: expected `Int`, found `(Array of Int) -> Bool`
 --> pipeline.science:5:5
  |
5 |     p.stages
  |     ^^^^^^^^ this is `(Array of Int) -> Bool

The one thing that cannot be spelled. (T) collapses to T with no node of its own, so a one-parameter closure whose single parameter is a tuple has no spelling: ((A, B)) -> C parses as a two-parameter closure. This is a genuine hole, and it is closed by a convention rather than by grammar — pairs in Science are records, so the only tuples in F0 are the return shape of a fallible function, and none of those is passed as an argument. If that stops being true, the answer is a named record and not a third paren.

If you are arriving from Rust: the shapes are the same and three habits are not

type is struct, choice is enum, of is the angle brackets, and Box of T is Box<T> doing the same job for the same reason. What differs: there is no tuple struct and no positional constructor — a record's fields are always named at construction, and a choice variant's payload is the only positional thing in the language; T? is not Option<T>, because it has no methods, no constructor and no Some/None to match against — you test it with ? and use the narrowed place; and an alias is written type N is T, with is rather than =, because the language has no = token at all.

Coming from Python: a choice is not an Enum class — its variants carry typed payloads and a match over it must be exhaustive, which is the whole reason to prefer it to a string constant. And a type is not a dataclass with defaults: there are no default field values, so every field is written at every construction.

Zero-based, and why that is not an aesthetic choice

Science is zero-based, ranges are half-open, and a[-1] is an error rather than the last element. The one-based column — Fortran, MATLAB, R, Julia, Mathematica, Lua — is not a list of bad languages; it is close to a list of the languages a computational physicist learned in, and Julia in particular is the closest thing Science has to a direct competitor.

The argument is not elegance and it is not familiarity: it is the zero-copy membrane. A NumPy array and a Science tensor over the same buffer are looking at the same bytes, and there is no marshalling step where an index could be adjusted — that absence is the feature. If the two languages disagreed about which element is [0] the disagreement would be silent, since both indices are in range; undetectable by the compiler, since the wrong index was computed in Python; undetectable in review, since both sides read correctly and only the composition is wrong; and numerically plausible — a spectrum shifted by one channel, a batch off by one row, a time series lagged by one sample.

There is a second, internal argument: every one-based language pairs one-based indexing with inclusive ranges, and Science's counting loop is 0..n, half-open, which was decided when ranges were. The cost lands on the computational-physics audience, who index from one in every paper they have ever read, and there is no cheap mitigation; offset-configurable arrays were considered and refused, because two conventions in one program is the failure the decision exists to prevent, and because they would make the index obligation above unprovable in general. It is also irreversible: no formatter rewrite turns one-based source into zero-based source, because the compiler cannot tell an intentional a[1] from a transcribed one.

Slices borrow

samples[1..5] has type Slice of T, which is { borrowed T, Int } — a pointer and a length — and it does not copy. Copying is not a close call: a column of a ten-gigabyte frame is pitched as the actual contiguous buffer, and a copying slice would mean taking half of it costs five gigabytes and a memcpy. The mutable form is MutableSlice of T and is produced through IndexMutably. The rank rule is NumPy's on purpose: an index position that is an integer drops its axis, and one that is a range or a bare .. keeps it. In F0 a slice is contiguous and one-dimensional over Array; strided and multidimensional views are F1, on Tensor, because a column of a row-major matrix is not contiguous and { ptr, len } cannot represent it.

Ownership needs no new rule for any of this. A slice is a borrow, so an array that has been sliced cannot be pushed to while the slice is live — push takes mutable self and the borrow rule forbids it — and "mutate while iterating" and "write through a view of the thing you are reading" are the same compile error. That is the NumPy aliasing bug, the one where a view of the array you are writing to produces a wrong answer with no error, removed by machinery that exists for unrelated reasons. It also costs something every NumPy user will hit once: let s be a[1..5] pins a for as long as s lives.

How a body is checked

Signatures are fully annotated; bodies are fully inferred. Checking is bidirectional and there is no unifier across function boundaries: every call site knows its callee's types before it looks at the arguments, and every body has a known expected return type, which gives a checking mode where the type is known and a synthesis mode where it is not. There is no Hindley–Milner, no generalisation, no let-polymorphism and no principal types. Global inference was rejected on two grounds: it does not hold up in the presence of interfaces and regions, and its errors point far from the fault — which, for a language whose diagnostics are the only teaching channel it has, is disqualifying.

Three things follow, in the order the design ranks them. Every diagnostic can point at an annotation a human typed. Bodies check in parallel and in any order, which is what makes the incremental boundary a function rather than a component — the memoised unit is one body, keyed on its hash plus the signatures it references, so editing a body invalidates that body and editing a signature invalidates every body that calls it. And it is expressible in Science, which matters because the compiler intends to compile itself: a bidirectional checker is a recursive walk with an environment, where a unification-based one wants a mutable union-find with interior mutability, which the language has no spelling for.

Local inference variables still exist, because let xs be (Array of Int).new() has to get its element type from a later push. So there is a small unification engine inside one body; it is bounded by the body and discarded when the body is done. Numeric literals go through it: an unsuffixed literal is inferred and only defaulted to I64 or F64 when nothing constrains it, because a language that silently makes 1 an I32 will be wrong on somebody's index arithmetic.

The auto-borrow is not in the type relation, and the measurement that forced the distinction is worth quoting. A parameter declared borrowed T is called with a T: the caller does not write the borrow and the checker inserts it. That is an elaboration, not a coercion — the value is unchanged and what the checker writes down is a Borrow node the author did not — so it lives in the body checker rather than in assignability, whose own table knows nothing about regions. The first run of the finished checker over the corpus produced 147 diagnostics, roughly 60% of which were a borrow the language had told the author not to write. Its cost is two places where the checker's tree no longer matches the token stream one to one, which MIR pays rather than the reader.

The practical consequence of all this is that you write types at a boundary and nowhere inside one. It is also why tools --json can derive a schema before anything is run: the parameter types are already written down.

The parser tests for a named argument by looking for an identifier then a colon, and it splits arguments on the top-level comma first. So a two-parameter closure written with a comma would have its second half, b: a + b, satisfy the named-argument test exactly, and the call would parse — silently — as two arguments. SC0137 is allocated for it.

What is not written down anywhere is how a closure captures. The design says the two forms "capture the same way" and never says what that way is — there is no by-borrow-versus-by-move rule, no move analogue, no closure-value type, no statement about storing one in a field, and no Fn-style hierarchy, neither adopted nor rejected. Every attested use is an immediate argument to a chain method. One consequence is fixed in advance for a reason unrelated to ergonomics: a closure must be typed by its captures rather than erased, from F0, because a future .parallel() has to reject a closure that captures something mutable borrowed, and nothing in F0 reads that information — which makes it the requirement most likely to be quietly missed.

If you are arriving from Python: def is a borrowed word, and the language knows it

The word is the same and the declaration is not. def introduces every function form there is — a free function, a method inside a has block, a required or defaulted member of an interface — so there is no second spelling to learn. Parameters carry types, the return type follows ->, and there is no implicit receiver: self is a parameter you write, and writing it is what makes a function a method rather than an associated one.

It is worth knowing that the design note that introduced def argued against it and lost. The rule was that a keyword is a whole English word, and def is a word with four letters removed. The familiarity argument, examined, counted the spelling across the languages this audience actually writes — Fortran FUNCTION, MATLAB function, R function, Julia function, JavaScript function, PHP function, Python def — and came out six to one against, with the six including the three languages the project names as its competition. The conclusion in the note is that familiarity does not favour def: it favours Python, and Python is one dialect of the audience rather than the audience.

It was adopted anyway, by the owner's decision. What survived is not a veto but an obligation to record: a shortened keyword must beat that audience test, and if it is adopted without beating it, it is named in a register. The register has two entries, const and def. function is now an ordinary identifier — you may bind it, name a field with it, even write def function(…) — and writing it where a declaration belongs is a migration diagnostic rather than a stray-name error.

One collision the audit missed, because it audited physics and chemistry and not compilers: def is ordinary compiler vocabulary, and this language intends to compile itself. The central table of every compiler maps a definition id to a definition and the field is called def. It was called that here too, in examples/21_compiler_shapes.science, and the rename broke it on the first run. The field is definition now, and that is the standing recommendation.

An interface is a set of requirements a type can satisfy. It may carry required methods, default bodies that call them, and associated types. Implementations are statically resolved.

Interfaces are named as verbs for what an implementor does — Iterate, Display, Inspect, Summarize — and the method is the same word in lower case, which keeps write the free function and Write.write the method in different namespaces.

The orphan rule applies, and it is one of the few rules in this section the compiler enforces. An implementation is legal only if the interface or the type belongs to the module declaring it. Without it, two libraries can each implement one interface for one type, both compile, and the program that uses both has two answers to one question with no way to say which it wanted — decided by the linker. Operators on primitives do not go through an implementation either, and the mechanism is not what it looks like. A design amendment said the operator interfaces are implemented for borrowed operands of the primitives; asking the compiler, they are not. What happens is that a borrow of a Copy type coerces to a value at each operand, so the checker sees F32 + F32 and never asks about a borrowed implementation. Copy and Clone are the two that will catch you. Copy means assignment duplicates instead of moving, and it is for small values whose duplication is a register move. Clone means duplication is explicit and possibly expensive. Every numeric type, Bool and Char are Copy; String deliberately is not, because an owned copy of a String allocates and calling that a copy would hide the allocation. A type that is neither — which is most types — moves when you assign it, and that is the subject of the next section.

Interface objects, and what dispatch costs

any I is the interface object: one function in the binary rather than one per type. There are four spellings and they cost different things. borrowed any I is a pointer paired with a vtable known at the site and emits no code at all — it is unsizing, and it is implicit. any I and Box of any I own the value, which means it moves to the heap, which allocates, and those two are written out rather than inserted. And (any I)? is a nullable fat pointer whose niche lives in the data pointer, so it is two words and not three.

That is the line the implicit-conversion set is drawn on, and it is worth stating because counting the variants gives a different answer than the design does. The rule is no implicit change of a value, not no implicit conversions — boxing preserves the value where the From widening that was deleted did not. By that measure there are two implicit conversions that change a value, and the implementation carries seven coercion variants: T into T?; a concrete error into any Error at a return and at an argument; borrowed C into borrowed any I for any interface; and borrowed T into T when T: Copy, in three shapes. A reader counting variants and concluding the note is stale is reading the right number and the wrong question.

One rule keeps interface objects usable at all: a method whose signature mentions Self by value is automatically excluded from the vtable, with no user-written bound to say so, and calling it on an any I value is SC0271. That is what lets any Iterate exist despite the combinators all consuming self.

The Copy rule that lets a borrow be read as a value

A shared borrow of a Copy type is assignable to the type itself. borrowed Int where an Int is wanted reads the value out, because the whole content of Copy is that a copy of the value is the value: no allocation, no drop, no observable second thing. Three conditions, each refusing something different — the borrow must be shared, so that mutable borrowed T does not become usable wherever T is; the referent must be exactly the target, so the rule takes one borrow off and composes with nothing else; and the referent must actually declare Copy, which a bare T: Copy bound on a type parameter does not.

It is in the language because the alternative was an expressive dead end. Science has no dereference operator, by design, and Array.get returns (borrowed T)? — so before this rule there was no spelling that read a Char out of a container. It is also what makes the most-written loop in the language legal: Array of T iterates at borrowed T, so for n in numbers: binds n as a borrow and every arithmetic operator in every loop body meets one. Without the rule, total be total + n is a type error.

The design is candid that this is a weaker rule than the other implicit conversions in the language: unsizing a borrow into an interface object emits no code at all, and this one emits a copy, so "the same value" is doing work that "no work happens" did before. It earns the weaker defence by the dead end, not by convenience — and the back end refuses it today, so the loop it exists to permit type-checks and does not yet build. changing

An interface is a Rust trait, not a Go interface: it is implemented explicitly, by a block that names both sides, and there is no structural conformance — a type with the right methods does not satisfy an interface it never claimed. Dispatch is static by default and any I is dyn Trait, right down to the fat pointer. The orphan rule is Rust's, for Rust's reason.

Ownership and borrows#

Memory is managed at compile time. Every value has exactly one owner; assigning, passing or returning moves that ownership unless the type is Copy; leaving scope destroys the value. There is no garbage collector, no reference counting, and no lifetime annotations to write.

Why a scientific language wants this at all

Ownership is usually sold as memory safety, and for this audience that is the least interesting thing it buys. Four concrete reasons, none of them abstract:

Device memory. Garbage collectors and GPUs are enemies. A GC does not know about device memory pressure, so a program runs out of GPU memory while host memory is fine and the collector sees no reason to run. Julia's CUDA support carries that wound permanently. Ownership frees a device buffer at a program point the compiler can name.

In-place updates without aliasing bugs. NumPy's slicing returns views, and a view that aliases the array you are writing to produces a wrong answer with no error. Futhark invented uniqueness types solely so that a pure language could write x[i] = v in place and stay correct; ownership is the same guarantee with a better surface. Silent view aliasing becomes a compile error.

Random keys that cannot be reused. A splittable generator is neither Copy nor Clone, and splitting consumes it. Reusing a JAX key returns the same numbers, is valid Python, and is the best-known footgun in that library. Here it is use-after-move, SC0301, a compile error — and it falls out of ownership rather than being a feature anybody added. This is the one place Science is designed to be strictly stronger than the best existing practice in the field, and it is also the one place the compiler does not yet keep the promise. See below.

No pauses, which matters for acquisition, control loops and MPI ranks, where a collector deciding to run is a missed deadline rather than a hiccup.

The cost is paid at the surface, and it will surprise every NumPy user exactly once: a large array assigned to a new name moves, and the old name is dead. Auto-borrow removes the most visible part of it; the diagnostics carry the rest. 

type Doc:
    title: String
    body: String

    source: borrowed Doc           # a record may hold a borrow; the region is inferred

    doc.title be title

    left.title is right.title

The rules, in full, are six lines. Every value has one owner. Assigning, passing or returning moves it unless the type is Copy. Using a moved value is SC0301. A value may be borrowed shared any number of times, or exclusively once, never both at once. No borrow outlives its referent. Leaving scope destroys the value, running Drop if it has one. Everything else in this section is a consequence of those six.

Rule three is not enforced, and nothing else on this page is in that state

SC0301 and SC0302 — use after move — are not implemented. No crate constructs either code. A program that passes an owned value to two functions in a row checks clean, and the second call reads memory the first one released. The MIR crate carries the move analysis the check would need and deliberately declines to share its lattice with a check that does not exist, which is an honest place to be and not a finished one.

It matters more than a missing diagnostic usually does, because print of a String moves its argument. Printing the same binding twice is a use after move, it compiles, and the second line comes out empty — see Strings and formatting. Every other ownership rule below is checked by a pass that runs on every sciencec check; this one is the hole. changing

Auto-borrow at call sites. If a parameter is declared borrowed T, the caller writes compare(a, b) and not compare(borrowed a, borrowed b). The signature still says borrowed, so a reader keeps the information; only the noise at the call site goes. Rust rejected this and Mojo adopted it, and for this audience Mojo is right — a scientist reading gemm(&a, &b, &mut c) is reading three sigils that tell them nothing they could not have read in the signature. An explicit borrow stays legal where it clarifies, and it is required where the position is not a call site, as in the View construction above.

The rule was almost lost, and how it was found is the argument for it. The design note that owns type checking never mentioned auto-borrow; the core spec requires it; and the implementation followed the note. The first run of the finished checker over the example corpus produced 147 diagnostics, roughly 60% of which were a borrow the language had told the author not to write. A rule the spec states and the design note forgets is worse than one neither has, because the implementation follows the note.

What a region is, and why you never write one

A region is the set of program points at which a borrow is live. That is a control-flow property, not a lexical one: a borrow ends at its last use, not at the closing of a block. The compiler assigns a fresh region variable to every borrow and to every reference inside a type, collects outlives constraints from assignments, calls and returns, propagates them to a fixed point, and then checks for conflicts. It does this over a control-flow graph, which is why the compiler has a mid-level IR at all.

There are no elision rules, because elision is not the mechanism. Rust's lifetime elision is a convenience over a syntax that remains available when the guess is wrong; Science has no syntax to fall back on, so a function's parameter and return regions are simply an analysis result. Functions are analysed in reverse topological order of the call graph, and mutual recursion is resolved by a fixed point over each strongly connected component. Once you are willing to read the body, guessing from the signature is strictly worse than reading it.

A type gets one region variable per borrowed field, and the relation between them is inferred at each use site rather than declared once. Where Rust writes FftwPlan<'a> and puts 'a on both fields — asserting the two outlive the same thing — Science asserts nothing, and each construction generates its own constraints. That keeps information Rust's single name discards. It costs two things: a type's region stops being a property of the type and becomes a property of each value, and the intersection of two field regions can be empty, which means a value that is dead at birth and needs its own diagnostic rather than a generic conflict. That diagnostic, SC0335, exists and has never fired; the crate's own argument is that with no upper bound in the solver it cannot, and it is kept because the argument is about the shape of the solver rather than about programs.

What happens when inference has no single answer. Rust reports an error and makes you write 'a. Science cannot make you write anything, so it refuses the program: SC0340, with the offered fix being to return an owned value or an index instead. That is uncomfortable — it rejects a program for being ambiguous rather than wrong — and it is the honest consequence of removing the syntax. In the implementation it turned out narrower than specified: a return constrained by two parameters is not ambiguous, because the answer is a set and the caller intersects it, so what is left is a body that returns a reference and does not say where it points. If SC0340 fires often in real code, the no-syntax decision is wrong, and the design says so rather than assuming otherwise.

One thing the claim does not say, and should not be read as saying. Region inference is interprocedural within a crate. Across a crate boundary the inferred relation — for each return region, which parameter regions constrain it — is serialised into crate metadata, because otherwise a module could not be checked without its dependencies' bodies. That summary carries exactly the same information a lifetime annotation does. The claim is that a programmer never writes a region. It was never that the compiler does not need one.

The inline body rule is about expressions, not about lines. In if a: b else: c the then-branch stops at else because else cannot continue an expression — fitting on one line is a consequence of that rule, not the rule. An inline body may be an expression, an assignment, or return / break / continue. It may not be a let, which would bind a name nothing could then use; that is SC0109. A dangling else binds to the innermost if.

while is not in the language. A condition-driven loop is loop: with an early break, which is two lines longer. That is Go's trade and its known cost, taken for a specific reason: ranges already cover the counting case while is usually misused for, and the language would otherwise carry two forms where one does. loop while condition: was considered and held back, because it reintroduces exactly the second form this decision exists to remove — and it is source-compatible to add later if the verbosity is genuinely felt.

Ranges use .., never :. 0..n is half-open and 0..=n is inclusive, so for i in 0..n: is the counting loop and there is no off-by-one to memorise. The colon is not available for a slicing notation because : already opens blocks and separates match arms, fields, named arguments and bounds, and a character with five jobs cannot take a sixth. Ranges sit below everything on the precedence ladder, so 0..n - 1 counts to n - 1.

for x in xs: borrows. It is the same construct as xs.iterate(), so iterating a collection does not consume it, and consuming is written out with iterate_consuming(). This is a deliberate correction of the single most-reported wart in Rust's collection API, where for x in v silently moves and burns every beginner once. The prelude keeps the promise: Array of T implements Iterate with Item is borrowed T, so the loop variable is a borrow, and the Copy rule is what makes arithmetic on it legal.

match is exhaustive, and the diagnostic for a missing case is the witness — the value nothing covers, printed as source you can paste. An arm is inline after its :, or an indented block.

The witness is the message, deliberately. A diagnostic that says only "not exhaustive" makes the reader re-derive what they missed, which for a record pattern means working out which combination of fields no arm reaches. So the compiler prints uncovered values — Point(x: 0, y: y), in the shape the reader can paste into a new arm — in the declaration order of the choice, with , and N more when the list is long.

A wildcard _ arm switches exhaustiveness off, and that is the trade: use a wildcard where the cases are genuinely open-ended (an integer, a character) and name every variant where they are not. The difference shows up the day somebody adds a variant — a wildcard absorbs it silently, and a complete set of arms stops the build in every place that has to decide what to do about it.

And a wildcard that covers nothing is an error too. An arm no value reaches is SC0537, and there is no attribute to silence it, because an arm is checked and lowered whether or not anything reaches it — a dead one is code that cannot run and therefore cannot be found to be wrong. 

error[SC0537]: no value reaches this arm
 --> render.science:9:9
  |
9 |         _: "other"
  |         ^ every value this matches is matched above
  |
  = note: an arm is checked and lowered whether or not anything reaches it, so a dead one is code that cannot run and cannot be found to be wrong; there is no attribute that silences this, so the fix is to delete the arm or to move it above the one that shadows it

A variant may be written qualified or bare: Plain and Format.Plain are the same pattern. The bare form is what a match arm usually wants, since the scrutinee's type already says which choice is meant; the qualified form is there for when two choices in scope have a variant with the same name.

Record patterns match by field name, and _ inside one means this field, whatever it is. Note that Point(x: x, y: _) binds x and ignores y: the name left of the colon is the field and the thing right of it is the pattern, which is the same order construction uses.

Arms are tested in order, one at a time; there is no decision tree. That is a statement about the generated code rather than about the language, and it is here because it is observable: a two-variant choice lowers to two comparisons and not one jump table, so a match is not a constant-time dispatch and a long one is a chain. The reordering that would make it one is an optimisation nobody has written.

The three pieces, and what each one is

T? is a nullable type — a T, or null. It replaces Option of T, and it is the spelling Kotlin, Swift, TypeScript and C# all share, so it needs no teaching. There is no wrapper: the present case is the value, which is why a body can satisfy a -> String? by producing a String, and why an exhausted iterator just returns null. It is a distinct type and not a union: T coerces into T? and T? never coerces to T, and T?? does not exist.

-> (Config, ConfigError?) is a pair, received by destructuring at the binding: let config, err be read_config(path). A function with nothing to hand back returns the error alone, because the pair would have () in its first slot and a name bound to that could do nothing.

? is a presence test and it is total. This is the piece most likely to be misread. It looks like Rust's propagation operator and it is not it: err? is a Bool, true when the value is not null. It never returns from the enclosing function, never unwraps and never fails. print(f"{pending?}") prints false or true. The character was free because the earlier design removed the propagation operator, so it now means exactly one thing.

? sits on the tightest rung, with call, index and field access, and applies to the whole postfix chain to its left. config.port? is (config.port)? and next()? is (next())?. It reads in the opposite direction from the prefix try it replaced, which covered the chain that followed it — which is why this was a rewrite of that rung and not a rename. Narrowing, exactly

Narrowing is a flow-sensitive fact about a place — a local, or a field projection from a narrowed place — and it is invalidated by any write to that place or to a prefix of it. config.port? narrows config.port and not config; writing to config invalidates it and writing to config.other does not. not err? narrows the other way round, and and narrows both operands in the then-branch.

An early return inside if err?: narrows err to null for the rest of the function, and that single rule is what makes the Go shape bearable: after the three lines that handle the failure, the compiler agrees with you that there is no failure left. A narrowing established before a loop does not survive the back edge unless it survives every path through the body, because the meet is intersection.

One dependency is worth knowing because it fixes an order: a narrowing is invalidated at the point an exclusive borrow is created, not where that borrow writes. That makes the type checker depend on a fact the region checker proves, and the two run in that order — which is why check's phase list has types before regions and not the other way about.

Error is a one-method interface — def message(self) -> String — so Error? in a return position is shorthand for (any Error)?. The shorthand exists because the long form appears in the signature of every fallible function in the language, and -> (Config, (any Error)?) is not a signature anyone should have to read.

The choice between the two forms is real and it is the author's. A concrete error type — usually a choice — keeps match exhaustive and costs no allocation, so it is right when the caller is expected to tell the cases apart. The interface form composes across a library boundary and boxes, so it is right at the top of a program where the only question is what to print. The rule of thumb: a library exports a concrete type, an application uses Error?.

Conversion between error types is written out, at the return. There is no implicit widening — which is exactly what the removed try did invisibly by calling From, and no section of the old design ever said that it did, which is how two files in the example corpus came to depend on an unspecified conversion. Making it explicit closes that hole by construction, and the price is visible above: StartupError.from_config(err) is a call you write. What is implicit is one step and only one: a concrete error type coerces to any Error at a return and at an argument, and nowhere else.

The prelude ships two concrete error types, IoError and TextError, and three functions that produce them: read_file(path) -> (String, IoError?), write_file(path, text) -> IoError?, and String.parse_int/parse_float, which return (I64, TextError?) and (F64, TextError?).

What this costs, stated plainly

Three lines per fallible call instead of one. The call, the if err?:, and the return. This is Go's well-known tax and it is real: when the corpus file for this feature was rewritten against the new model it roughly doubled in length. The argument for paying it is that the error path is then written where it happens, in the order it happens, for a reader rather than for a writer — and the premise of the whole design is that this code is mostly read.

Nothing in a type forces the error to be read, and that is the serious one. A Result made ignoring a failure a type error; a returned Error? can be dropped on the floor, which is Go's problem and Go pays for it. The mitigation is SC0140, and it has shipped: a binding of a nullable error type that is never tested with ? before the function returns is a compile error rather than a lint.

A pipeline is mostly glue: load, reshape, filter, batch, hand to a model, collect, write. The arithmetic in the middle is somebody else's library; the part you write is the part between the libraries, and it is a chain of method calls.

Adapters are lazy; terminals are eager; there is no eager mode. docs.iterate().map(each.title) allocates nothing and touches nothing until a terminal pulls it, which is why it is legal over a forty-gigabyte file. Six adapters over a million rows allocate six million-element arrays eagerly and none lazily, and take(5) after a map does five units of work lazily and a million eagerly. Three adapters are barriers and buffer the whole stream — sorted(), sorted(by:) and reverse() — which is why putting a .sorted(…) before a .discard(…) sorts rows you are about to throw away. That is the one performance trap laziness leaves open, and it is a documentation problem rather than a language one.

Two closure forms, and the one case that needs the second

each names the subject of the enclosing call without declaring it. It is the shorter form and the one most chains want. It is not a loop word — iteration is for x in xs, and naming a closure's subject is the only thing each does, which is why it is reserved: letting a program shadow it would make every chain ambiguous.

name giving expression declares the parameter. It is required when the parameter is used more than once, and for the one case each cannot express: nesting. In outer.map(each.inner.map(each.x)) the two each refer to different subjects and the inner one shadows the outer irrecoverably. Science rejects that rather than picking a rule: 

error[SC0115]: a nested `each` would name a different subject than the `each` around it
 --> chain.science:5:29
  |
5 |     docs.map(each.title.map(each.length()))
  |                             ^^^^ this `each` is inside another `each`
  |

Two each in the same argument are fine — they are the same subject — so only an enclosing each is an error. Having two spellings for one idea is design debt, and it is recorded as deliberate: Kotlin and Swift carry the same debt and it has not hurt them.

What ownership does to a chain

A chain value is a borrow of its source, wearing a long type. iterate() takes a shared borrow and each adapter moves that borrow forward into itself, so let titles be docs.iterate().map(each.title) leaves titles borrowing docs, and pushing to docs before the chain is consumed is a borrow error. Put the other way round: a chain freezes its collection for its whole life, so "mutate while iterating" is a compile error rather than a rule in the manual. That is the most valuable thing ownership buys this API.

Because regions are flow-based rather than lexical, running the terminal before the mutation is not an error at all — the borrow ends at its last use. Had the language chosen lexical lifetimes, stored chains would be close to unusable. A chain is also neither Copy nor Clone and terminals take it by value, so a half-consumed chain cannot be silently observed twice.

Items that were borrowed stay borrowed all the way into collect(), and the printed type tells you: Array of borrowed Doc is a set of views into something else, Array of Doc is yours. The rule that makes this bearable is the copy-out rule — a place expression returned from a closure yields the value when its type is Copy and a borrow otherwise — so .map(each.weight) on an F32 field gives F32 and .map(each.title) on a String field gives borrowed String. The escape is one link: .owned().

In F0 a chain cannot cross a function boundary. Writing -> MapOver of (Keep of (ArrayIterate of Doc, …), …) in a signature is not a language anyone should ship, so a function returns a collection and materialises with .collect(). That costs one allocation per boundary, and the boundary is where a pipeline wants something concrete anyway: what you hand to the next stage is a dataset, not a recipe. Libraries return named source types; user functions return collections.

Calls always take parentheses, including when they take no arguments: text.length(), never text.length. The parenthesis-free form reads better in a chain and was considered; once functions are values, doc.summary is ambiguous between calling it and naming it, and a language cannot resolve that by guessing. Parentheses mean call; their absence means a field.

Five item forms, and each earned its place against a real library. def declares an undefined symbol resolved at link. type … is … spells a C typedef. const … be … as … transcribes a #define or an enumerator. static names an exported data symbol: HDF5's H5T_NATIVE_DOUBLE is not a constant — the header defines it as (H5open(), H5T_NATIVE_DOUBLE_g) — and CPython has 199 such globals. union is an opaque blob of a known size and alignment, which is the normal path for a C union rather than an unpleasantness that does not arise. symbol decouples the Science name from the linker name.

symbol exists because of the worst FFI bug in scientific computing. BLAS and LAPACK ship in two incompatible builds — 32-bit integers and ILP64 — with identical function names, identical argument counts and identical semantics, differing only in the width of eight of dgemm's thirteen arguments. Link the wrong pair and the result is not a crash: it is correct answers for small matrices and silently wrong answers for large ones. The ILP64 builds that matter ship distinct symbols, so naming them separately turns a wrong answer at run time into an undefined symbol at link time. Where a vendor ships ILP64 under the same names — Intel MKL does — nothing can detect the mismatch, and the binding has to say so in a comment, because that is the only warning available.

Why the block is unsafe at all. An extern declaration is a claim about code the compiler will never see: that a symbol of this name exists, that it takes these arguments in this order with these widths, that it does not retain the pointers it is given, that it does not free them. None of that is checkable. Writing the declaration is therefore itself the unsafe act, and the keyword belongs where the act is. Rust reached the same conclusion in its 2024 edition after a decade of extern blocks that looked safe.

What unsafe does not suspend is the part worth reading, because it is the part users of other languages assume is suspended. Type checking, trait resolution, ownership, borrow checking, region inference, overflow checks, bounds checks and exhaustiveness all still apply. unsafe means one narrow thing: the compiler's model of memory it can see is intact, and what you are about to do involves memory it cannot see. If an unsafe block is long, the binding is written wrong.

Named arguments are permitted at a foreign call site, and nowhere else in the language outside record construction. The reason is domain-specific and decisive: cblas_dgemm takes thirteen arguments, two of which are transposition flags that look identical, and confusing them produces a wrong answer rather than an error. This is the call every numerical Science program makes, and it has to be readable by someone checking a formula against a paper. Two call conventions in one language is design debt, and it is recorded as deliberate.

ffi.Span of T is a pointer and a length. At the ABI only the pointer crosses; the length exists on the Science side alone, for one reason — so that the wrapper's precondition, that lda * n does not exceed the buffer, is an expression the compiler type-checks rather than a comment. It is the raw material for a check, not the check itself.

The aliasing rule BLAS states in its own documentation — "C must not overlap A or B" — turns out to be the rule the borrow checker already enforces. A wrapper taking two shared borrows and one exclusive one makes gemm(a, b, a) a borrow error, caught by machinery that exists for reasons unrelated to FFI — and unlike most of this page, that machinery runs today. Likewise a handle type with a Drop implementation: C's "call the destructor exactly once" is Science's ownership, so a cudnnHandle_t wrapped as a handle is destroyed exactly once, on every path out including early returns, at a program point the compiler can name. There is no goto cleanup and no way to forget one.

What cannot be checked, as a list

Written as a list so that a reader can see whether their problem is on it. Retention — that the callee does not keep a borrowed pointer past the call — is unstatable and unverifiable, and the borrowed keyword in an extern declaration is the assertion. Signature agreement with the real header. Reentrancy through C. setjmp/longjmp across Science frames, which skips every destructor and is undetectable. A library calling exit. Bitfields and variadics.

And the largest practical risk, which is about linking: the linker checks that a symbol exists and nothing else. C object files carry no type information, so a wrong argument count, integer width or struct layout links cleanly and corrupts the stack at run time. The first implementation therefore refuses by-value aggregate arguments entirely and requires pointer-to-aggregate, because BLAS, LAPACK, HDF5, cuDNN and MPI pass aggregates by pointer anyway — a restriction that can be lifted source-compatibly later. F16 and BF16 may not cross by value because C has no agreed by-value ABI for half precision: _Float16 is passed differently by GCC, Clang and MSVC. That wart is felt exactly where it hurts most, in mixed-precision training, and the alternative is an ABI that is right on one compiler and silently wrong on another.

Both of those refusals have codes of their own — SC0429 and SC0431 — and neither is what you will see. The renderers exist and need a span to print; what reaches the refusal is a call site inside a body, so the message arrives as SC0400 carrying the same sentence. The day the refusal carries a span the two collapse into one. It is a small thing and it is the kind of small thing a reference gets wrong by copying a table.

Tools and schemas#

tool declares a callable exposed to a model. It is a second function-declaration form, and it exists because it carries obligations a def does not — every one of which a compiler can check. 

choice LineShape:
    Gaussian
    Lorentzian
    PseudoVoigt

type Peak:
    centre: F64
    width: F64

## Fit Bragg peaks in a window of flight time.
##
## Uses the run's own dark-current subtraction. Fails if the window holds
## fewer than 32 channels, because the fit is then underdetermined.
tool fit_peaks(
        ## The run identifier, as printed in the run log.
        run: String,
        ## Lower edge of the window, in seconds from the pulse.
        window_lower: F64,
        ## Line shape to fit. PseudoVoigt is the usual choice.
        line_shape: LineShape,
        ## At most 32; the fit is underdetermined above that.
        max_peaks: U8) -> Int:
    0

## Expose the same computation to a human caller.
def helper(run: borrowed String) -> Int:
    run.length()

The thesis is that the schema is the signature. Every other way of exposing a function to a model writes it twice — once as a handler the compiler checks and once as a JSON Schema nothing checks — and the two copies sit next to each other inviting a reader to believe they agree. When they drift, the failure is invisible: the schema says a parameter is a string, the handler indexes it as a list, and the model is told something false about a function it is deciding whether to call. Here there is no second artefact and therefore nothing to drift from.

Why a keyword rather than a marker. A marker that changes nothing is an attribute, and a language should not spend a word on an attribute. tool earns one because it has five obligations def has not, and a compiler checks every one: every parameter type must survive a round trip through JSON Schema; it may not be generic; no parameter may be borrowed; it must carry a ## description; and its return type is constrained. Two more come from where it may stand — module level only, and never with a self receiver.

Each of those is an argument rather than a rule. Not generic, because the list a caller is given is flat and concrete with one schema per entry, so there is nothing for T to be instantiated at. Not borrowed, because there is no caller to borrow from: the arguments were built from what arrived a moment ago and the tool is the only owner there is. Not a method, because a tool is called by name alone and there is nothing for self to be bound to.

The description is mandatory, and only here

A tool with no ## run above it is SC0190, an error, and one whose summary line is blank is SC0195. This is the only construct in Science for which documentation is mandatory, and the justification is deliberately narrow, or it becomes "document your code", which a compiler has no business enforcing. Everywhere else a doc comment is read by somebody who has already decided to call the function. Here it is read by the caller in order to decide, so the string is an argument rather than prose — and the failure it prevents is invisible: an undescribed tool does not fail, it is simply never chosen, and no test catches that.

The mapping's honest edges. U64 gets a minimum and no maximum, because 264−1 is not exactly representable as a JSON number and emitting it would be a lie about what the other side can send. F32 and F64 both become {"type":"number"}, so the wire is wider than the type. A T? parameter is its payload's schema with the name left out of required, because JSON's "absent" and "present and null" are two states Science has one of, and the language does not pretend otherwise. Toolchain#

Seven commands, no configuration, no plugins. A file argument to check, build or resolve is the entry of a crate, and the directory it sits in is the crate root.

CommandDoes
sciencec check FILE…The whole front end: lex, parse, resolve, type-check, lower to MIR, infer regions. Reports every file, continuing past a broken one.
sciencec build FILE…Check, then emit an object file, link it against the runtime archive, and write the executable beside the source. One file is one crate is one executable.

There is no run and no test. Dumps go to stdout, diagnostics and the 3 errors, 1 warning summary to stderr. Exit 0 when nothing was reported as an error, 1 when something was; warnings alone do not fail, so a CI job can gate on the exit code without arguing about lint levels. A file that cannot be read is an error like any other: it is reported, it sets the exit code, and the remaining files are still checked. There is no colour, so NO_COLOR is honoured trivially — the UI suite compares diagnostic text byte for byte, and escape codes in the driver would mean re-rendering diagnostics somewhere other than where they are rendered.

build writes beside the source and not into the working directory, which is the one place it differs from cc and rustc. The working directory is an environment-dependent input, and sciencec build examples/hello.science would otherwise put the executable somewhere that depends on where you were standing. The cost is that a build writes into the source tree, which is the wrong default the day there is a target/ directory to write to instead — and there is no package manager yet, so there is not one.

build needs a backend compiled in. The default build of sciencec reports SC0400 naming the feature and the install command; cargo build -p sciencec --features llvm produces the one that links. The backend binds LLVM-C dynamically, so LLVM's bin directory has to be on PATH or the compiler will not start — before main, with no diagnostic, which is the platform's behaviour and not the compiler's.

fmt writes to stdout unless --write is given, and it refuses any file that does not already lex and parse. That refusal is the whole safety property: reformatting a file whose token stream is a guess is how a formatter eats a program. It requires syntax and deliberately not resolution, because a formatter works on syntax and a file importing modules that are not present is still a well-formed program. It also reads exactly the files it was named and never a module one of them imports: rewriting a file the user did not ask about is not something a use line should be able to authorise.

The formatter is why one spelling per operation matters. The earlier design carried both a word form and a symbol form for all six comparisons and called the duplication debt worth taking. It was not: a formatter cannot canonicalise between a == b and a is b, because the choice depends on the operands' types, and a formatter that must run after type checking is not a formatter. The two spellings were permanently un-normalisable, which for a language whose code is largely machine-written means permanent drift. One spelling each cannot drift, and removing the second form took five words off the reserved list as well. The same argument is what refuses comprehensions.

The formatter owns the only two diagnostics in the language that a compiler can never produce: SC0900, the formatter finding that its own output does not parse back to the program it was given, and SC0901, an unmatched # fmt: off. They live in a band, SC0900–SC0999, that the core spec's table does not have — it was recorded in the design index after the formatter had already taken two codes with no band to take them from, and it still needs ratifying. A complaint from a program that reads Science is not a complaint from one that compiles it, and filing it under a compiler phase would make the phases mean less.

Doc comments, and why they survive the lexer

A run of ## immediately above a declaration is a doc comment. Unlike an ordinary # comment it is carried on the token it documents rather than discarded, so it survives into the syntax tree and onward to anything that reads a signature — which is how tools --json produces a description nobody wrote twice. This has to happen in F0 and it cannot be retrofitted: once the lexer discards them, every tool downstream is built assuming they are gone. The consumers — a documentation tool, help(), doc tests — are F1. The preservation is not.

A ## run may attach to a module, a function, a method, a type, a choice, an interface, a type alias, a const, a field, a variant, or an implements block. A run attached to nothing — at the end of a file, or separated from the next declaration by a blank line — is SC0176, a warning whose fix is "make it #". The content is Markdown and the first line is the summary; there are deliberately no @param or @returns tags, because the parameter list is already in the signature and a tag duplicating it is a second copy to drift.

The composition with ordinary comments is the part a docstring form cannot manage. # TODO next to a doc comment is an ordinary comment and does not become documentation. And a docstring would only ever cover functions: a record field, a choice variant, a const, a type alias and a module all want documenting and none of them has a body to put a string in. A docstring in a compiled language would also be an expression statement with no effect that the compiler silently treats as metadata, which is the one thing the language refuses to do anywhere else — resolve an ambiguity by guessing.

Reserved words

    Held for later phases — using one is an error

      Deliberately not reserved

        The first list is the lexer's, word for word. Reserving costs nothing now and breaks every program using the name later, which is the whole argument for a list this long — but the second list has a known price and this audience pays it. shape, model and tensor are reserved globally, so x.shape and let model be … do not compile. That was accepted deliberately, so that the tensor and agent phases are guaranteed their syntax; the alternative considered was making them contextual keywords recognised only in declaration position. You will meet it the first time you try to name a parameter shape.

        The third list is free on purpose: grad, dim, dims, axis, device, dtype, unit and alias are each a common variable name in the code of the people this language is for, and that outranks the convenience of reserving them. f and r are not reserved either, although they are string prefixes: the prefix is recognised only immediately before a quote, so let f be 1 stays legal.         Two words moved recently, and both moved into the first list. function left every list and is now an ordinary identifier — a program may bind it, name a field function, or write def function(…) — because the parser recognises the old declaration positionally, and a contextual test costs one line of lookahead where a reservation would cost an identifier the audience uses. tool went the other way, from "reserved for later" to a declaration keyword, because it now checks five things a def does not; a marker that changed nothing would have stayed a reservation. The band is appended rather than the table repartitioned, because renumbering codes that are already implemented and already asserted in the UI tests would buy nothing. A code's band says which phase owns it; it does not say when the band was drawn.

        Six code collisions have been found so far, and every one of them was invisible to the note that caused it, because each had honestly checked against everything that existed when it started. Two of the six were worse than a collision: they were a conflict somebody had already resolved, in a file the allocation table did not reach. That is now the expected failure rather than a surprising one, and the table is scanned against itself rather than read.

        Twenty-two worked programs live in examples/; they are input data for the compiler's own test suites, so anything there that fails to lex, parse, resolve, type-check or borrow-check is a bug in the compiler rather than a typo to be quietly patched. Programs that must fail, each paired with the exact diagnostic they have to produce, live in tests/ui/.
