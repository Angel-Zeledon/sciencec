Guide · six features, one chapter each

The six things Science does that your other language does not

The tutorial teaches the language: bindings, functions, types, ownership. This page assumes you have read it and teaches the six features that are the actual reason to choose Science for scientific work. Each chapter starts with a bug — a real one, the kind that reaches a published figure — and then builds the construct that makes that bug impossible, one line at a time.

Read at whatever pace you like; the chapters do not depend on each other. But read each one in order inside itself. Every chapter is written to be understood without skipping, and none of them assumes you already know why the feature is a good idea. If a paragraph seems slow, it is slow on purpose: these are the six places where a reader who half-understands will write something that compiles and is wrong.

How to read this page#

A short orientation, and one honest warning about what these six features have in common.

Every chapter has the same four parts, in the same order. First, the bug — a program that looks correct and is not. Second, the idea — in one sentence, before any syntax. Third, the construct, built up a line at a time with nothing introduced silently. Fourth, the cost, because every one of these features asks you to type something you did not type before, and a guide that hides the bill is selling rather than teaching.

What the six have in common is the shape of the bug they catch. None of these features catches a crash. A program that crashes tells you it is broken, and you fix it that afternoon. Every bug on this page is one where the program finishes, prints a number, and the number is wrong — the average over a sample that quietly shrank, the matrix that was transposed and happened to be square, the cached result from code you edited an hour ago. These are the expensive bugs in scientific computing because nothing tells you they happened.

A note on the code blocks. Science on this page is coloured by the same highlighter the rest of the site uses, so a keyword here looks like a keyword everywhere. Where a chapter shows a compiler message it is shown once, in the one place where reading the message is the lesson. There is deliberately not a diagnostic beside every example: this is a guide, not the reference, and a page that alternates code and error boxes teaches the errors rather than the language.

1 · property — testing the cases you did not think of#

You already know how to write a test. This chapter is about the fact that a test only ever checks the input its author imagined, and about the construct that checks the ones they did not.

The bug

Here is a function that computes the mean of a list, and a test for it. Both look fine. Read them and decide whether you would approve this in a review. 

def mean(xs: &Array[F64]) -> F64:
    let mutable total be 0.0
    for x in xs:
        total be total + x
    total / (xs.length() as F64)

test "mean of three numbers":
    testing.check_close(mean(&[1.0, 2.0, 3.0]), 2.0, tolerance: 1e-12)

The test passes. The function divides by zero on an empty list and returns NaN, and that NaN will flow through every subtraction and comparison downstream of it without stopping anything. The author did not think of the empty list, so the test does not contain it, and no amount of care fixes this in general — the whole problem is that you cannot write a test for the case you did not think of.

The idea

Instead of writing down an input and its answer, write down something that must be true of every input, and let the compiler's test runner generate the inputs. A statement that holds for all inputs is called a property, and it is spelled with that word.

The construct

Start with the simplest possible one. It reads almost like English: for any array of integers you like, sorting it does not change how many elements it has. 

property "sorting preserves length" for xs: Array[Int]:
    testing.check_equal(sorted(xs).length(), xs.length())

Three parts, and each is worth naming. property is the item keyword, and like test it takes a sentence in quotes rather than an identifier, because the name is what you read in a failure report and a sentence reads better than test_sorting_preserves_length. The for xs: Array[Int] clause declares what to generate and its type. The body is an ordinary block using the same testing.check* functions a test uses — nothing new to learn there.

When you run sciencec test, the runner calls that body a few hundred times with different arrays: empty ones, single-element ones, long ones, ones full of duplicates, ones containing the largest representable integer. You wrote one line and got the empty-list case for free, which is exactly the case the test above was missing.

Narrowing what gets generated

Often a property only holds for some inputs. The mean of an empty list is not a number, so a property about it has to exclude the empty list. You do that with where, the same word a generic bound uses: 

property "mean lies between the smallest and largest value"
        for xs: Array[F64] where xs.length() > 0:
    let m be mean(&xs)
    testing.check(m >= xs.min() and m <= xs.max())

A where clause discards generated inputs that do not satisfy it. That is simple to understand and it has one trap, so the language checks for it: if your condition throws away almost everything, the property silently ends up testing three inputs instead of three hundred and you would never know. Science refuses to run a property whose filter rejects more than nine tenths of what is generated, and tells you to generate the narrower thing directly instead — x: Positive[F64] generates only positive numbers and discards nothing.

Shrinking, which is the part that makes it usable

Suppose the property above fails. The input that broke it is whatever the generator happened to produce — realistically an array of forty numbers like -3.27e11, which tells you nothing at all. A counterexample you cannot read is barely better than no counterexample.

So before reporting a failure, the runner shrinks it: it repeatedly tries smaller, simpler versions of the failing input — fewer elements, values closer to zero — and keeps any that still fail. What it finally shows you is the smallest input it could find that still breaks the property, which is usually so small that the bug is obvious from looking at it.

This is why, in Science, shrinking is required rather than optional. A type you want to generate must implement Arbitrary, and that interface has two methods, not one: 

interface Arbitrary:
    def generate(key: &Key, size: Int) -> Self
    def shrink(self) -> Array[Self]

Most languages make shrink optional and the result is that half the types in a codebase have it and half do not, so half your failures are readable and half are not. Requiring it costs a few lines when you write a generator for your own type, and it means every failure on every type is readable. For an atom — a type with nothing smaller to try — shrink returns an empty array and you are done.

The failure, and why it always reproduces

Here is the one compiler-adjacent output in this chapter, because reading it is the lesson: 

failed: mean lies between the smallest and largest value
  shrunk to: xs = [0.0, 0.0]
  seed:      k:7f3a1c04e7b2   size 13
  wrote:     tests/regressions/mean_lies_between.science

Look at the last two lines, because they are where Science differs from every property-testing library you may have used. The seed is printed, and a regression file is written.

The seed matters because a property that fails once and then cannot be made to fail again is not a test result — it is a rumour, and you cannot debug it. Science's random generator is seeded rather than ambient, so sciencec test --seed k:7f3a1c04e7b2 reproduces the entire run exactly, on any machine, today or in four years. The seed also goes into the provenance record that chapter 6 describes, so a failing run is reproducible from the artefact and not only from your terminal scrollback.

The regression file matters for a different reason. It is not a cache file — it is ordinary Science source, a test item with the shrunk input written out as a literal: 

# Generated by `sciencec test` on a failing property.
test "mean lies between min and max — regression":
    let xs be [0.0, 0.0]
    let m be mean(&xs)
    testing.check(m >= xs.min() and m <= xs.max())

Because it is source, it shows up in a pull request where somebody reviews it, it keeps working after you delete the property that produced it, and it is committed to the repository instead of living in a cache directory that is nearly always in .gitignore. The bug found on your machine on a Tuesday is still being tested on the build server next year.

What it costs

Two things, and both are real. Thinking of a property is harder than thinking of a test case — "what is true of every input?" is a genuinely different and more demanding question than "what does this return for 3?", and it is a skill that takes a week or two to develop. And a property run is slower than a test, because it runs hundreds of times instead of once. The usual arrangement is properties for the handful of functions at the core of your analysis and ordinary test items for everything else, and the two live side by side in the same file with the same runner.

2 · requires and ensures — what a function promises#

Every function has rules about what you may pass it. Usually those rules live in a comment, or in the author's head. This chapter is about writing them where the compiler can read them.

The bug

# Find a root of `f` between `lo` and `hi` by bisection.
# Requires f(lo) and f(hi) to have opposite signs, and lo < hi.
def bisect(f: (F64) -> F64, lo: F64, hi: F64, tolerance: F64) -> F64:
    ...

That comment is doing real work and it has no power whatsoever. Call bisect(f, 10.0, 2.0, 1e-9) with the bounds the wrong way round and you get a number back. Not an error — a number, plausible-looking, wrong. The comment was right and nobody read it, which is the normal fate of comments.

The idea

Move the comment into the signature, where it becomes a contract: a statement the compiler is obliged to do something about. Not merely to record — to act on.

The construct

def bisect(f: (F64) -> F64, lo: F64, hi: F64, tolerance: F64) -> F64
    requires lo < hi
    requires tolerance > 0.0
    ensures result >= lo and result <= hi:
    ...

requires states what must be true before the function runs — a condition on the arguments, which is the caller's responsibility. ensures states what will be true after, and inside it the name result refers to the value being returned. Both sit after the return type and before the : that opens the body, and you may write as many of each as you like, one per line.

result is not a reserved word. It means the returned value only inside an ensures clause; anywhere else, including inside the function body, let result be … is an ordinary binding and keeps working. This is a deliberate pattern in the language — a word means something special in exactly one position and is yours everywhere else — and you will see it again in chapters 4 and 6.

The three rungs, which is the whole design

Now the important part, and the part that is different from the contract systems you may have met. When the compiler reads a contract, one of three things happens to it. Which one is not up to you and is not a setting.

Proved. The compiler works out that the condition is always true and emits no code at all. If you call bisect(f, 0.0, 10.0, 1e-9) with those literals, the compiler can see that 0.0 < 10.0 and that 1e-9 > 0.0, so both requires clauses cost nothing at runtime. The contract was free.

Checked. The compiler cannot work it out — the bounds came from a file, say — so it emits a check. If the condition is false when the program runs, the program stops with a message naming the contract and the call site. You pay one comparison, which is nothing next to a bisection.

Assumed. The compiler cannot prove it and cannot check it either, because the condition says something no runtime test can settle. Then the contract is recorded as an assumption and you get a warning, because a contract that is neither proved nor checked is a comment that happens to have syntax, and you deserve to know which of your contracts are doing nothing.

You can see which rung each of your contracts landed on. This is the command that makes the whole feature honest, because without it the ladder would be invisible: 

$ sciencec contracts ./src
src/bisect.science:9   requires lo < hi                     checked
src/bisect.science:10  requires tolerance > 0.0             proved   (callers: 3/3)
src/bisect.science:11  ensures  result >= lo and ...        checked
src/stats.science:44   invariant value >= 0.0 and ...       assumed

The fourth outcome, which is the best one

There is one more thing that can happen and it is not a rung. Sometimes the compiler can prove a requires is false: 

let root be bisect(f, 10.0, 2.0, 1e-9)   # the bug from the top of the chapter

10.0 < 2.0 is false, and the compiler can see it. That is not a failed proof and not a runtime check — it is a bug caught at compile time, reported at the call site, before the program has ever run. This is the best thing contracts produce and it is worth writing a contract for even if every other one you write lands on "checked".

Invariants on your own types

The same idea applies to a type. A probability is a number between zero and one; saying so in the type means no probability anywhere in your program can ever be outside that range: 

type Probability:
    value: F64
    invariant value >= 0.0 and value <= 1.0

The invariant is checked after the value is constructed, and after any method that takes mutable self finishes. That second rule is only possible because of ownership: while such a method runs, Science's ownership rules guarantee nobody else holds a reference to the value, so checking once at the end is enough. In a language where anything can alias anything, this construct needs an entire theory; here it falls out of a rule you already learned in the tutorial.

assert teaches the compiler

You have met assert already as a runtime check that stops the program. It still does that. What is worth knowing is that it is on the same ladder, which means an assert now does something for you besides checking: 

def take_first(xs: &Array[F64], n: Int) -> Slice[F64]:
    assert(n <= xs.length())
    xs[0..n]

Ordinarily xs[0..n] compiles to a bounds check on every access. Here the assert has already established the fact the bounds check would test, so the compiler removes the check. You wrote a line for documentation and got a faster loop. This is the practical answer to "why would I bother with contracts if I do not care about verification": they make your hot loop faster, from lines you wanted to write anyway.

What it costs

The "proved" rung is narrower than you will expect, and floats are never on it. The compiler proves things about linear arithmetic on integers — comparisons, addition, multiplication by a constant — and nothing else. A condition involving a floating-point value is never proved, only checked, because rounding, NaN and signed zero make almost every intuitive claim about floats false in some corner. Write ten contracts in ordinary numerical code and you should expect most of them to come back "checked". That is still worth having — a checked contract stops a wrong answer from propagating — but if you were hoping the compiler would prove your numerical method correct, it will not, and no compiler will.

In a release build, ensures clauses are stripped and requires clauses are not. The reasoning: a requires catches your caller's bug and is usually one comparison, so removing it is how a library ships a hole; an ensures is you checking your own work, it is often the expensive one, and by release time your tests and properties have exercised it thousands of times.

3 · Missing data — the average that quietly changed its denominator#

Real measurements have holes in them. This chapter is about the single line of code where those holes turn into a wrong number, and about why Science refuses to write that line for you.

The bug

let heights be frame.column("height")     # some rows were never measured
let average be heights.mean()

Ask five languages what that average is and you get three different answers. pandas skips the missing values and divides by however many were left. NumPy with NaN propagates, so the answer is NaN — and the usual response to that is to add a nan_to_num upstream, which replaces "we did not measure this person" with "this person is zero metres tall". R propagates and makes you say na.rm = TRUE, which is the closest to right.

The harm is not the arithmetic. Skipping is a perfectly defensible thing to do. The harm is that you compared two columns of different completeness as though they were the same sample and nothing told you. A mean over 340 of 1,000 rows and a mean over 998 of 1,000 rows are different claims about the world, and they print identically.

The idea

There is no correct default here, because both answers are right in different studies. So Science does not pick one. It makes you say which you meant, and only in the places where there is actually something to decide.

The construct

First, how absence is written. You already know this from the tutorial and there is nothing new: a value that might be absent has type T?, and the absent value is null. Science deliberately has no second kind of absence — no NA beside null, no NaN-as-missing. One idea, one spelling. 

let heights: Array[F64?] be [1.72, null, 1.81]

Now the rule. A reduction — an operation that collapses a whole collection into one value, like mean, sum or max — over a collection that can contain null does not compile until you say what absence means: 

let m be heights.mean(skipping null)        # 1.765, the average of the 2 present values
let m be heights.mean(propagating null)     # null, because one value is absent

skipping null drops the absent values and divides by how many were left. propagating null gives null the moment any value is absent. Two words, each readable at the call site without looking up a signature — which is why they are these words rather than mean(x, true), a line nobody can check in a review.

Why this does not make your code noisy

This is the part people worry about, so it is worth being clear: the requirement is attached to the element type, not to the operation. An Array[F64] cannot contain absence, so xs.mean() works exactly as it always did. Only an Array[F64?] asks you anything.

That means the vast majority of your code is untouched, and it means the fix for a noisy pipeline is a real fix rather than an annotation. Deal with the absence once, near the top, and the type stops being nullable: 

let clean be heights.drop_missing()   # Array[F64] — no longer nullable
let m be clean.mean()                 # and no policy is needed, or accepted

The count travels with the answer

When you reduce with skipping null, Science records how many values it skipped, and that count goes into the run record described in chapter 6. So the fact that your average was over 340 of 1,000 rows is written down in the artefact, where a reviewer can find it, rather than existing only as something you would have had to check. This is the part of the feature that outlives your own session.

Two columns at once need a third word

Correlating two columns is where this gets genuinely subtle, and it is worth slowing down for. Suppose height is missing in rows 3 and 7, and weight is missing in rows 5 and 9. If you simply skip the absent values in each column independently, you end up with two lists of different lengths whose entries no longer line up — you would be correlating one person's height with another person's weight.

So for an operation over two aligned collections, plain skipping null is refused, and you write: 

let r be correlation(height, weight, skipping null pairwise)

pairwise drops row i from both columns when either one is absent, so the pairing survives. That is almost always what you meant, and the reason you have to type the word is that the version without it is a bug you would never have seen in the output.

What it costs

More typing, on a line you write constantly. That is the whole bill and it lands on exactly the people this feature is for. The defence is that the alternative is a default, and a default here is a decision made on your behalf that changes your published number. The risk the language accepts in exchange: if you respond by typing .drop_missing() at the top of every pipeline out of reflex, you have made a stronger assumption than the one you were avoiding — at least it is visible in your source, where the silent version was not.

4 · Named axes — the transpose that happened to be square#

Array programming's great strength is that one line of code does a million operations. Its great weakness is that a line which mixes up two dimensions is still one perfectly valid line. This chapter closes that.

The bug

let error be predict(weights, features) .- labels

Nothing in that line says which dimension is samples and which is features. Usually a mistake here produces a shape mismatch and you find out immediately. But when the two dimensions happen to be the same length — and in machine learning they are square constantly: a 768×768 covariance matrix, a batch of 768 samples with 768 features — transposing one of them is not a shape mismatch. It is a valid computation, it produces numbers of the right size, and the numbers are wrong.

The idea

Give the dimension a name. Then two dimensions that are both 768 long but mean different things are different types, and mixing them up is a compile error instead of a plausible number.

Science can do this where Python cannot, and the reason is worth understanding: the shape of a tensor is already part of its type here. A Tensor[F32, (96, 2048)] carries those numbers in its type and the compiler already checks them. Adding a name to each dimension is one more field in a structure that exists, and it turns a runtime convention into a compile-time check.

The construct

Axis names are declared, with the axis item. You declare them once, usually near the top of a module: 

axis sample
axis wavelength

They are declared rather than conjured out of thin air on first use, and that is deliberate. If any identifier in a shape position created an axis, then wavelenght would silently be a different axis from wavelength, and a typo would reintroduce exactly the class of bug the feature exists to remove. Declaring them also means they are ordinary names: they live in your module, you export them with public, and two libraries agree on sample only when they mean the same thing by it.

Now use them in a shape, with name: length in square brackets: 

type Spectrum is Tensor[F32, [wavelength: 2048, sample: 96]]

The old unnamed spelling still works and means the same thing it always did. Tensor[F32, (96, 2048)] is a tensor whose axes are anonymous, every existing program keeps compiling, and naming is something you opt into. You can even mix them — [batch: n, 3, 3] is a named batch of anonymous 3×3 matrices, which is exactly how you would describe it out loud.

What the name actually does

Once axes have names, operations line them up by name and ignore their position entirely. That one sentence is the whole semantics. Everything below follows from it. 

# readings: Tensor[F32, [sample: 96, wavelength: 2048]]
# baseline: Tensor[F32, [wavelength: 2048]]
let centred be readings .- baseline

The wavelength axes match by name and are subtracted element-wise; sample exists on the left and not on the right, so the baseline is reused for every sample. You did not have to know which axis was first, and if you later reorder the type nothing here breaks.

Reducing along an axis you can name

You have probably written axis: 0 a thousand times. It has three problems: you cannot check it without reconstructing the whole pipeline in your head, any operation that reorders axes silently invalidates it, and it is a number rather than a meaning. So: 

let mean_spectrum be spectra.mean(over: sample)
for row in table.along(sample):
    ...

Two words rather than one, because these are two different operations. over consumes an axis — you average away the samples, and the result no longer has a sample axis. along walks an axis — you iterate over the samples, and each one still has all its other dimensions. English already makes this distinction and reusing one word for both is how NumPy's apply_along_axis ended up needing a paragraph of documentation.

Matrix multiplication states its own meaning

This is the chapter's best moment. When both operands have named axes, @ contracts over the axis name they share: 

# x: Tensor[F32, [sample: n, feature: 768]]
# w: Tensor[F32, [feature: 768, output: 10]]
let y be x @ w              # [sample: n, output: 10]

Both operands name feature, so that is what gets summed over. The result has the axes that were left. Notice what this buys: the operation says what it means, x @ w and w @ x are now the same computation, and the classic bug — a weight matrix that needed transposing and happened to be square — is a compile error, because the axis names would not line up. Most of the transposes in your code stop being necessary at all.

What it costs

Two libraries will define different sample axes and you will have to convert between them. This is the same tax any strongly-typed wrapper charges, and the mitigation is convention: standard axis names should come from one place rather than being invented per package.

Positional indexing into a named tensor is refused, not warned. Once a tensor has named axes, t[3, 7] is an error and you write t[sample: 3]. This is strict on purpose: a positional index is the thing that goes stale when axes are reordered, and leaving it available in code that opted into naming would leave the bug alive in exactly the place someone was trying to eliminate it.

5 · durable — the six-hour run that fell over at hour five#

Everybody who computes for a living has written a caching layer by hand, and everybody's has the same bug. This chapter is about putting it in the compiler, where the bug is fixable.

The bug

You know this code because you have written it: 

# The hand-rolled version, in any language. Delete the cache if you change
# anything in `fit` — and remember to, every time, forever.
let cache_path be f"cache/fit_{dataset_name}_{epochs}.bin"

The key describes the inputs. It does not describe the code. So you edit the body of fit, rerun, and get the old answer back in four milliseconds — and it looks exactly like a fast, correct run. You believe it. This is not a mistake careful people avoid; it is a mistake careful people make on a Friday afternoon, because nothing about the situation looks wrong.

The idea

The compiler knows what the code is. So let the compiler build the key, and put the compiled body into it. Then editing the function invalidates the cache by itself, with no discipline required from you.

The construct

durable def fit(data: &Frame, epochs: Int) -> Model
    keyed by (data.digest(), epochs)
    checkpoint every 10 epochs:
    let mutable model be Model.initial()
    for epoch in 0..epochs:
        model be step(model, data)
    model

Take it one clause at a time.

durable in front of def says the result should be cached. The cache lives in .science/cache/, entries are named by their key and never modified once written, and there is a size limit so your disk does not fill.

keyed by (…) is you saying what identifies a call. Notice that the arguments are not hashed automatically, and that is a considered decision rather than an oversight: your Frame may be forty gigabytes, and hashing it would take longer than the fit it was meant to save. You know what identifies your dataset — a content digest, a DOI, a run identifier — and the compiler does not. Every parameter must either appear in this clause or be listed as ignoring, so you can decide a parameter is irrelevant but you cannot forget one.

And the part the clause does not mention: in addition to what you wrote, the key automatically includes a hash of the compiled body of fit and of everything it calls, plus the build environment. Change one line inside step and the key changes, so the cache misses and the work is redone. That is the bug from the top of the chapter, fixed by the one participant that has the information.

checkpoint every 10 epochs saves the loop's state every ten iterations. If the job is killed at epoch 83, the next run starts from epoch 80 instead of from zero. This is where the six lost hours come back.

Why the compiler insists the function be pure

Caching means replacing a call with a remembered answer. That is only sound if the call had no other reason to happen. A function that reads a file, or the clock, or the network, does have another reason, and caching it gives you a stale answer that nothing detects.

Science already tracks this. Every function has an inferred effect set, and durable requires it to be empty — which is the same condition pure def asserts, so durable implies pure and writing both is redundant. If you try to make a file-reading function durable, the compiler declines and, importantly, shows you the chain — which call inside which function reaches the filesystem — because external is inferred rather than written and you would otherwise have to guess.

The fix is nearly always the same and it is a better program: read the file in the caller, pass the data in, and make the pure part durable. 

# Not durable: it reads the world, and a cached answer would not notice the
# file changing. Read here, and hand the data to the function that computes.
def main():
    let data, err be read_csv("measurements.csv")
    if err?:
        return
    let model be fit(&data, epochs: 200)

What it costs

A wrong keyed by is a wrong answer, and the language says so rather than pretending otherwise. If you key a fit on a dataset name while the file behind that name changes, you will get the old model. This is the one genuinely unsound thing in the chapter. It is unsound in exactly the direction your hand-written cache already was — so the feature is strictly better than the status quo, and it is not safe. For peace of mind, sciencec test --verify-cache recomputes durable functions and reports any disagreement with the cache; it is slow, and it belongs in a nightly build rather than in your edit-run loop.

Checkpointing writes real bytes. Saving a model every ten epochs is not free, which is why the default when you omit checkpoint every is to cache only the final result and write nothing in between. Caching the boundary is the cheap win; checkpointing is the expensive one, and you ask for it when the run is long enough to deserve it.

6 · with blocks — saying the seed once#

Four things get configured once at the top of an analysis and used everywhere in it: the random seed, the device, the float precision, and whether expensive checks run. This chapter is about setting them in a way that ends up in your paper's artefact instead of in your shell history.

The bug

You pass the seed through eleven functions by hand and one of them takes a different one. Or you set a global at the top and a library caches it, and now half your program is seeded and half is not. Or — most commonly — a reviewer asks what seed produced figure 3 and the honest answer is that nobody wrote it down.

The idea

A block that fixes a policy for everything inside it. Python's with statement has the right shape and Science borrows the shape. What it does not borrow is the mechanism, and the difference is the whole chapter.

The construct

with seed 42, device gpu:0, precision f32:
    let model be fit(&data, epochs: 200)

Four policies exist and the list is closed: seed fixes the random key, device fixes where tensors are allocated, precision fixes what an unannotated float literal becomes, and unchecked turns off contract checking for a hot block. You may give several in one head, separated by commas.

The important part: a policy is a value, not a global

Read this paragraph twice, because the obvious reading of the example above is the wrong one. with seed 42 does not reach inside the functions you call and change what they read. There is no hidden global being set and unset.

What actually happens is much simpler: seed 42 binds a value, named seed, in that block. A function that needs randomness declares a parameter for it, exactly as it would have to anyway. Nothing about any function changes; what changes is what is in scope to hand it.

The reason for this strictness is that Science tracks which functions read machine-supplied state — the clock, the entropy pool, the environment — and refuses to let that happen invisibly. A with block that silently redirected what a callee read would be exactly that hidden state, with nicer syntax. Python's context managers work the way they do because Python has no way to check; Science does, so it does not need to.

There is one concession, because threading key through eleven call sites is the tedium this construct exists to remove. Inside the block, an argument whose name and type match a policy binding may be left out, and it is filled in from the block: 

with seed 42:
    let a be bootstrap(&data, 1000)                   # `key` filled from the block
    let b be bootstrap(&data, 1000, key: other_key)   # written explicitly, and wins

This is decided when the program is type-checked, it is visible in the function's signature — bootstrap still declares key: &Key and still receives it — and sciencec fmt --explicit will write every omission back out if you would rather read them. It is the one place in the language where a value on a line did not come from that line, and it is bounded: the source is always a with head lexically above, in the same function.

A policy nobody uses is an error

This rule looks harsh and it is the most useful one in the chapter: 

with seed 42:
    let m be fit(&data)   # error: `fit` takes no key — nothing here is seeded

Unused variables are warnings everywhere else in Science. This one is an error because of what the mistake costs. The author of that block believes their fit is seeded. It is not. The run is irreproducible in the particular way that looks reproducible — the artefact would faithfully record a seed that did nothing at all.

Where it ends up

Every policy block that encloses a computation is written into the provenance record that Science stamps onto your outputs. So the question "what seed, what device, what precision, were the checks on?" is answered by the figure itself rather than by your memory. That is the point of the construct; the convenience of not retyping the seed is a side effect.

It composes with the shape-binding form of with you may have met, because they are clauses in the same head: 

with table.shape as [sample: rows, feature: 768], seed 42, precision f32:
    let z be (table .- table.mean(over: sample)) ./ table.deviation(over: sample)

What it costs

The filled-in argument is the contestable part. It trades a little locality — you cannot see where key came from by reading that one line — for the feature being worth using at all. The trade is bounded by scope and reversible by a formatter flag, and it is worth knowing that it is a trade.

precision is the one to be careful with. It decides what an unannotated literal becomes and what an unconstrained type defaults to. It does not reach out and narrow values that were computed outside the block — an F64 that flows in stays an F64 — and the compiler stops you if a block's precision would change the type of something bound outside it. A policy that silently changed the width of your data would be the worst feature in the language.

Putting it together#

One program using all six, so you can see what they look like in the same file rather than one chapter at a time. 

use testing (check, check_close)

axis sample
axis feature

## The fraction of variance the model explains. Never above 1, never below 0
## for a model that includes an intercept.
type RSquared:
    value: F64
    invariant value >= 0.0 and value <= 1.0

## Standardise each feature: subtract its mean, divide by its deviation.
## Pure, so it can be cached; the contract says what it promises.
pure def standardise(
        table: &Tensor[F32, [sample: n, feature: d]])
        -> Tensor[F32, [sample: n, feature: d]]
    requires n > 1
    ensures result.shape() is table.shape():
    let centre be table.mean(over: sample)
    let spread be table.deviation(over: sample)
    (table .- centre) ./ spread

## Expensive. Cached against the data, the settings, and this function's own
## compiled body — so editing the line below invalidates the cache by itself.
durable def fit(
        table: &Frame,
        epochs: Int,
        key: &Key) -> Model
    keyed by (table.digest(), epochs)
    checkpoint every 10 epochs:
    ...

def main():
    let raw, err be read_csv("measurements.csv")
    if err?:
        print("could not read the measurements")
        return

    # The heights column has holes in it. Say what that means, once, here —
    # and the count of skipped rows goes into the run record with the answer.
    let mean_height be raw.column("height").mean(skipping null)
    print(f"mean height {mean_height} over the rows that have one")

    # One place fixes the seed, the device and the precision for everything
    # below, and all three are stamped into the output's provenance.
    with seed 42, device gpu:0, precision f32:
        let model be fit(&raw, epochs: 200)
        print(f"fitted {model.name()}")

test "standardising twice is the same as standardising once":
    let once be standardise(&sample_table())
    check_close(standardise(&once), once, tolerance: 1e-6)

property "standardising never changes the shape" for t: Tensor[F32, [sample: 8, feature: 3]]:
    check(standardise(&t).shape() is t.shape())

Read it once more and notice what is absent. There is no comment saying "delete the cache if you change this". There is no note saying "seed is set at the top". There is nothing explaining which axis is which. Each of those comments has become something the compiler reads — and a thing the compiler reads cannot drift away from the code the way a comment does.
